Agent每日一题02：Agent 工具调用总出错？源头定义+执行校验+兜底纠错

发表于2026-11-06|更新于2026-11-06|技术学习
|浏览量:

1. 面试开场：工具调用为什么总是”翻车”

面试官常问：Agent 接入真实业务后，工具调用频繁出错，你会怎么排查和解决？

先给出结论：问题往往不是模型”不会思考”，而是工具调用环节缺少约束。典型表现有三类：

  • 选错工具：该查订单却调用了退款接口；该用搜索工具却调用了数据库查询。
  • 选错参数：工具选对了，但参数名写错、类型不对、必填项缺失，或把 order_id 填成了用户 ID。
  • 输出格式不匹配：返回的 JSON 不符合工具 schema，多一层嵌套、少一个字段，或把数字写成字符串。

三类问题本质相同：模型对”工具是什么、何时用、怎么用”理解不精确，系统又缺少约束与纠错机制。

答题框架：按”源头定义、执行校验、兜底纠错”三个维度展开——源头定义工具描述与参数 schema，执行环节做校验与规划，最后用重试与降级兜住残余错误。

2. 第一步：先定位，而不是笼统地”调 prompt”

面试官追问：你怎么知道问题出在哪？

答：先建立可观测性。没有数据支撑的调优，往往是在猜。建议在工具调用链路上记录以下字段：

字段 说明 用途
tool_name 模型选择的工具名 统计选错工具的比例
arguments 模型生成的原始参数 分析参数错误模式
schema_valid 是否符合工具 schema 衡量格式错误率
exec_result 工具执行结果/异常 区分”调用错”与”执行错”
retry_count 重试次数 评估纠错机制效果

有了这些数据，可以回答几个关键问题：

  • 错误集中在少数几个工具上，还是普遍存在？
  • 是工具描述有歧义，还是参数定义太复杂？
  • 格式错误是偶发，还是某个模型/某个工具组合的稳定问题？

经验上，80% 的工具调用错误集中在 20% 的工具上，而这些工具通常具备共同特征：名称相似、描述模糊、参数过多。

3. 源头定义一：把工具描述写成”使用说明书”

面试官追问：工具描述该怎么写？

答：工具描述是模型选择工具的唯一依据。

一个好的工具描述应包含四个要素：

四个要素对应如下：

  • 用途边界：写清”什么时候用”和”什么时候不用”，尤其是与相似工具的边界。
  • 参数说明：给出参数示例和格式约束，让模型有明确的参照。
  • 返回内容：说明返回什么，帮助模型判断这个工具能否满足当前需求。
  • 交叉引用：对容易混淆的工具直接点名”如果你要 X，请用 Y 工具”，显式引导模型选对工具。

4. 源头定义二：用 Schema 把参数”卡死”

面试官追问：参数错误怎么从源头减少？

答：参数错误很大一部分来自 schema 过于宽松。比如 type: "string" 的字段，模型可能填入 "null"、"undefined" 甚至一段解释性文字。

强化 schema 的几个手段：

  • 用 enum 限定取值范围，而不是让模型自由发挥。
  • 用 pattern 约束格式，如订单号、手机号、日期。
  • 用 required 明确必填项，避免模型”选择性省略”。
  • 减少参数数量，超过 5 个参数的工具考虑拆分。
  • 避免同名不同义的参数，比如两个工具都有 id，但一个指订单、一个指用户。

additionalProperties: false 这一项经常被忽略，但它能有效阻止模型塞入 schema 之外的字段。

5. 执行校验一：让模型”先想再做”

面试官追问：复杂任务怎么降低参数出错率？

答：直接让模型输出工具调用，容易在参数上出错。更稳妥的做法是引入显式的推理步骤：

  1. 先让模型输出”我要做什么、需要哪些信息、应该用哪个工具”。
  2. 再根据这个推理结果生成工具调用。
  3. 工具返回后，再判断是否需要下一步。

这种”先规划后执行”的模式，在 ReAct、Plan-and-Execute 等框架中已有成熟实践。它的价值在于：把隐式的决策过程显式化，让错误在早期暴露。

6. 执行校验二与兜底纠错：校验、重试与降级

面试官追问：约束做到位了，还需要兜底吗？

答：再好的约束也无法保证 100% 正确，所以必须有兜底机制。

6.3 降级与人工兜底

当重试仍失败时，不要无限循环。可以：

  • 切换到更简单的备用工具；
  • 返回结构化错误，引导用户补充信息；
  • 把调用失败的原因返回给模型，引导其修正参数或更换工具；
  • 转人工处理，并记录失败样本用于后续优化。

7. 整体流程

把上述策略串起来，一个健壮的工具调用流程如下：

flowchart TD
  A["用户请求"] --> B["规划阶段：意图识别与工具选择"]
  B --> C{"信息是否充足"}
  C -->|"否"| D["向用户追问"]
  C -->|"是"| E["生成工具调用参数"]
  E --> F{"Schema 校验"}
  F -->|"失败"| G["错误回传模型修正"]
  G --> H{"是否超过重试次数"}
  H -->|"否"| E
  H -->|"是"| I["降级或转人工"]
  F -->|"通过"| J["执行工具"]
  J --> K{"执行是否成功"}
  K -->|"否"| G
  K -->|"是"| L["返回结果给模型"]
  L --> M{"任务是否完成"}
  M -->|"否"| B
  M -->|"是"| N["输出最终答案"]

8. 面试收尾：直接吟诵这句话

答：工具调用出错，根因通常不在模型能力，而在三处约束缺失。其一，工具描述不清：模型只能依据描述判断工具用途，描述含糊会直接导致选错工具或选错参数。其二，参数约束不足：schema 过于宽松，非法输入也能通过，错误被带入执行阶段。其三，失败缺少兜底：单次调用失败即报错，没有校验、重试与降级，局部错误被放大为整体故障。对应解法同样分三层：源头把工具描述与 schema 定义清楚，降低首次出错概率；执行环节引入规划与校验，在真正调用前拦截错误；最后以有限次重试和降级处理残余失败，保证单次失败不影响任务整体完成。三层补齐后，Agent 的稳定性会有明显提升。
