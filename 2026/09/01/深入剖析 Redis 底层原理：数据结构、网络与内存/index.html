数据结构

Redis 之所以能以极高的性能处理各种数据类型，其核心在于精心设计的底层数据结构。这些结构在内存使用效率和操作速度之间取得了精妙的平衡。

动态字符串SDS

Redis构建的一种新字符串结构，简单动态字符串SDS（Simple Dynamic String）。它并非直接使用 C 语言的原生字符串（以 \0 结尾的字符数组），而是进行了以下关键优化：

  1. 常数时间复杂度获取字符串长度：SDS 在结构头部存储了字符串的当前长度（len），因此 strlen 操作的时间复杂度是 O(1)，而 C 字符串需要 O(N)。
  2. 杜绝缓冲区溢出：SDS 在修改前会检查剩余空间（free），如果不足会自动进行扩容，避免了 C 字符串拼接时可能发生的缓冲区溢出问题。
  3. 减少内存重分配次数：SDS 采用了空间预分配和惰性空间释放策略。
    • 空间预分配：当 SDS 需要扩容时，不仅会分配所需空间，还会额外分配一定的空闲空间（free）。下次再追加时，如果空间足够就直接使用，减少了连续字符串增长时频繁重分配的开销。
    • 惰性空间释放：缩短字符串时，多出来的空间不会立即归还给系统，而是更新 len 并增加 free。后续如果再次增长，可以直接利用这部分空间。
  4. 二进制安全：SDS 使用 len 属性来判断字符串是否结束，而不是 \0。因此可以安全地存储包含 \0 的数据（如图片、音频等），使其不仅可以保存文本，还能保存任意格式的二进制数据。

IntSet

IntSet是Redis中set集合的一种实现方式，基于整数数组来实现，并且具备长度可变、有序等特征。它的设计目标是内存效率和性能。

intset 结构包含三个属性：

  • encoding：编码方式，决定每个元素占用多少字节（INTSET_ENC_INT16, INTSET_ENC_INT32, INTSET_ENC_INT64）。
  • length：集合包含的元素数量。
  • contents：一个柔性数组，按顺序保存集合中的元素。数组中的元素类型由 encoding 决定，并且所有元素都按值的大小升序排列，且不包含重复项。startPtr + (sizeof(int16) * index)

升级操作是整数集合的一大亮点。当添加一个新元素，且其类型比现有集合中所有元素的类型都要长时（例如，向一个 int16_t 的集合中添加一个 int64_t 的值），整数集合会先进行升级：

  1. 根据新元素的类型，扩展底层数组的空间大小。
  2. 将现有元素全部转换成与新元素相同的类型，并放置到正确的位置上（ 从后往前移动，防止覆盖）。
  3. 将新元素添加到底层数组。
  4. 修改encoding属性，length属性
    升级操作一旦完成，就无法降级。升级带来了灵活性，可以随时将不同类型的整数添加到集合中，而不必担心类型错误，同时也节约了内存（只在必要时才使用更大的类型）。
    插入时底层采用二分查找。

Dict

字典，又称符号表、关联数组或映射，是 Redis 的基石。Redis 的数据库本身就是一个大字典，所有键值对都存储在其中。此外，哈希（Hash）类型也是使用字典实现的。
Dict由三部分组成：哈希表、哈希节点、字典

向Dict添加键值对时，Redis首先根据key计算出hash值h，利用h & sizemask来计算元素应该存储到数组中的哪个索引位置。

扩容

Redis 的字典使用哈希表作为底层实现。为了解决哈希冲突，它采用了链地址法（Separate Chaining）。每个哈希表节点包含键、值和指向下一个节点的指针，形成一个链表。
Dict每次新增键值对都会检查负载因子（LoadFactor = used / size），满足以下两种就会触发哈希表扩容：

  • LoadFactor >= 1，并且服务器没有执行BGSAVE或者BGREWRITEAOF等后台进程；
  • LoadFactor > 5；

Redis 的字典实现包含两个哈希表（ht[0] 和 ht[1]），这是为了支持渐进式 rehash。

  • Rehash 触发条件：当负载因子（已保存节点数 / 哈希表大小）超过一定阈值时，会触发扩展；当负载因子低于一定阈值时，会触发收缩。按照新的size申请内存空间，创建dictht，并赋值给dict.ht[1]
  • 渐进式过程：Rehash 不是一次性完成的，而是在字典的每次增、删、改、查操作中，检查dict.rehashidx是否>-1，是则将顺带将 ht[0].table[rehashidx] 中的一个索引上的所有键值对 rehash 到 ht[1]，并且rehashidx++。这样就将庞大的计算量平摊到了多次操作中，避免了服务长时间停顿。
  • 将dict.ht[1]赋值给dict.ht[0]，给dict.ht[1]初始化为空哈希表，释放原来的dict.ht[0]内存。

新增操作，直接写入ht[1]，查改删会在ht[0]、ht[1]溢出查找执行，保证ht[0]只减不增，随着rehash最终为空

ZipList压缩列表

压缩列表（ziplist）是列表（List）、哈希（Hash）和有序集合（Sorted Set）在元素数量较少、元素值较小时使用的底层实现之一。它是一个为节约内存而设计的顺序型数据结构。

一个压缩列表可以包含任意多个节点，每个节点可以保存一个字节数组或者一个整数值。其组成如下：

  • zlbytes：记录整个压缩列表占用的内存字节数。
  • zltail：记录表尾节点距离起始地址的偏移量，用于快速定位尾节点。
  • zllen：记录节点数量。
  • zlend：特殊值 0xFF，标记列表末端。

每个节点（entry）由三部分组成：

  1. previous_entry_length：记录前一个节点的长度，占1个或5个字节，用于从后向前遍历。（start-previous_entry_length=pre）
    • 如果前一节点长度<254字节，则采用1个字节来保存这个长度值。

      1 个字节 = 8 位（bit），能表示的无符号整数范围是 0 ~ 255。
      在 ZipList 的编码规范中，数值 255（即二进制的 11111111）被预留为特殊标记（ZIP_END），用于标识 ZipList 的末尾。
      因此，1 个字节实际能表示的最大长度只有 254。

    • 如果前一节点长度>254字节，则采用5个字节来保存这个长度值，第一个为0xfe，后四个才是真实长度数据。
  2. encoding：记录当前节点所保存数据的类型（字符串还是整数）和长度。占用1个、2个或5个字节。
  3. content：保存节点的实际数据。
    （next = start+previous_entry_length+encoding+content）

注意 ZipListEntry所有存储长度的数值采用小端字节序，即低字节在前面，高字节在后面。0x1234，采用小端存储0x3412

Encoding编码

encoding编码分为字符串和整数，用于记录当前节点所保存数据的类型和长度。其编码规则如下：

1. 字符串编码

字符串编码的前两位（最高两位）决定了编码类型和后续长度信息的存储方式：

  • 00：表示存储的是长度小于等于 63 字节的字符串。encoding 占用 1 个字节，格式为 00xxxxxx，其中后 6 位 xxxxxx 表示字符串的实际长度（0-63）。
  • 01：表示存储的是长度小于等于 16383 字节的字符串。encoding 占用 2 个字节，格式为 01xxxxxx yyyyyyyy，其中后 14 位（xxxxxx yyyyyyyy）表示字符串的实际长度（0-16383）。
  • 10：表示存储的是长度大于 16383 字节的字符串。encoding 占用 5 个字节，格式为 10xxxxxx（第一个字节固定为 10，后 6 位未使用），后跟 4 个字节的大端序 32 位无符号整数，表示字符串的长度（最大 2^32-1）。

2. 整数编码

整数编码的前两位固定为 11，表示存储的是整数。后续位用于区分整数的具体类型和值：

  • 11000000：表示存储的是 int16_t 类型的整数（2 字节）。
  • 11010000：表示存储的是 int32_t 类型的整数（4 字节）。
  • 11100000：表示存储的是 int64_t 类型的整数（8 字节）。
  • 11110000：表示存储的是 24 位有符号整数（3 字节）。
  • 11111110：表示存储的是 8 位有符号整数（1 字节）。
  • 1111xxxx（其中 xxxx 的范围是 0001 到 1101）：这是一个特殊编码，表示存储的整数就是 xxxx 所表示的值（范围 1-13）。因为 0000 和 1110 已被占用，所以实际可表示的整数范围是 1 到 13，减1后为真实值0~12（可以省去content）。这种编码方式无需额外的 content 字段，整数直接存储在 encoding 的低 4 位中，极大地节省了空间。

ZipList的连锁更新问题

  • 触发场景：
    假设当前 Entry 的前驱节点长度是 253 字节，所以当前 Entry 的 prevlen 只占了 1 字节。
    此时，如果我们在前驱节点之前插入了一个超大元素（比如 300 字节），导致前驱节点的长度从 253 变成了 300（>=254）。

  • 连锁反应：
    为了记录这个 300，当前 Entry 的 prevlen 必须从 1 字节 扩展为 5 字节。
    当前 Entry 因此变长了 4 个字节。
    这多出来的 4 个字节，会导致下一个 Entry 眼中的“前驱节点长度”发生了变化（变长了 4）。
    如果这个变化正好跨过了 254 的阈值，下一个 Entry 的 prevlen 也得跟着从 1 字节改成 5 字节，然后再引发下下个的变动……以此类推，像多米诺骨牌一样传播。

  • 实际影响：
    虽然最坏情况下是 O(N^2) 的复杂度，但 Redis 官方和大量实测证明，这种情况在真实业务中极少触发，且受影响的节点数量通常很小。正因 ZipList 内存节省带来的巨大收益，Redis 接受这个微小的风险，并将 ZipList 作为底层默认结构（在 Redis 7.0 后被 Listpack 替代，正是为了彻底解决连锁更新问题）。s

listpack

listpack 通过重新设计节点结构，从根本上避免了这个问题。
在 listpack 中，一个节点（Entry）由三部分组成：

  • encoding-type：编码类型，用于解析后面的数据。
  • data：实际存储的数据。
  • backlen：记录当前节点自身的长度。
    这个 backlen 字段是关键。它和 ziplist 的 previous_entry_length 不同，记录的是自己的长度。

backlen 采用了从后向前解析的设计：

  1. 当程序需要从当前位置找到前一个节点时，它会从当前节点的起始位置向左逐个字节地解析。
  2. 通过解析 backlen 字段，程序就能知道当前节点的长度，从而计算出前一个节点的起始地址。

这样，无需在每个节点中存储前驱信息，也能高效地实现双向遍历。
这种设计让 listpack 在保持内存紧凑的同时，彻底根除了连锁更新的隐患。

SkipList跳跃表

跳跃表是一种有序数据结构，它通过在每个节点中维持多个指向其他节点的指针，从而达到快速访问节点的目的。Redis 使用跳跃表作为有序集合（Sorted Set）的底层实现之一（当元素数量较多或成员是较长的字符串时）。

SkipList由 zskiplist 和 zskiplistNode 组成。

  • zskiplist 结构保存跳跃表信息，如头尾节点、长度和最大层数。
  • zskiplistNode 代表跳跃表节点。每个节点包含：
    • 层（Level）：每层包含前进指针和跨度。层是随机生成的，层数越高概率越低。这决定了查询的效率，高层指针可以“跳跃”过许多节点，加快查找速度。
    • 后退指针：用于从表尾向表头遍历。
    • 分值（Score）：一个 double 类型的浮点数，所有节点按分值从小到大排序。
    • 成员对象（obj）：一个指向 SDS 字符串的指针，成员对象必须唯一，但分值可以相同。

跳跃表支持平均 O(log N)、最坏 O(N) 复杂度的节点查找，并且其有序性使得范围操作（如 ZRANGE）也非常高效。

五种数据类型

String

String是Redis中最常见的数据存储类型，其值可以是字符串、整数或浮点数。String类型支持丰富的操作命令，如SET、GET、INCR、APPEND等。

编码方式

String类型根据值的不同，采用三种编码方式以优化内存和性能：

  1. INT：当字符串对象保存的是整数值，并且这个整数值可以用long类型表示时，对象会将整数值直接保存在ptr属性里（将void*转换成long），并将编码设置为int。这种编码方式最节省内存。

  2. EMBSTR：当字符串对象保存的是一个字符串值，并且这个字符串值的长度小于等于44字节（Redis 3.2+版本，之前是39字节）时，对象将使用embstr编码。embstr编码是专门用于保存短字符串的一种优化编码方式，它将redisObject结构和SDS结构在内存中连续分配，从而只需要一次内存分配操作，且能更好地利用缓存局部性。

  3. RAW：当字符串对象保存的是一个字符串值，并且这个字符串值的长度大于44字节时，对象将使用raw编码。raw编码会调用两次内存分配函数来分别创建redisObject结构和SDS结构。

注意：44字节作为分界点：
48(SDS：44+4(3(len+alloc+flags)+1(\0)))+16(RedisObject)=64=2^8
redis底层内存分配方式为gmLock，刚好是一片内存大小(x^n )，不会产生碎片

ZSet

ZSet（有序集合）是 Redis 中一个非常重要的数据结构，它结合了 Set 和 Sorted List 的特性：每个元素都是唯一的（成员唯一），但每个元素都会关联一个分数（score），元素按照分数进行排序。

ZSet 的底层实现有两种，根据元素数量和元素大小自动选择：

  1. SkipList + Dict（跳跃表 + 字典）：
    • 当元素数量或元素大小超过 ZipList 的限制时，ZSet 会转换为 SkipList（跳跃表） + Dict（字典） 的组合结构。
    • Dict（字典）：存储 成员 -> 分数 的映射，用于 O(1) 时间复杂度查找指定成员的分数。
    • SkipList（跳跃表）：存储 分数 -> 成员 的映射，并按分数排序，支持范围查询和排名操作。

这种组合结构充分利用了两种数据结构的优势：

  • Dict 保证了根据成员查找分数的高效性（O(1)）。
  • SkipList 保证了根据分数范围查询、排名操作的高效性（平均 O(log N)）。

  1. ZipList（压缩列表）：
    • 当元素数量较少（默认 zset-max-ziplist-entries 128）且每个元素的大小较小（默认 zset-max-ziplist-value 64 字节）时，ZSet 使用 ZipList 作为底层实现。

  • 在 ZipList 中，元素和分数是连续存储的score和element是紧挨着一起的两个entry，按分数score升序排列。这种实现非常节省内存。

Hash

Hash（哈希）是 Redis 中用于存储字段-值对（field-value pairs）的数据类型，非常适合表示对象（如用户信息、商品属性等）。每个 Hash 可以存储多达 2^32 - 1 个字段-值对。

Hash 的底层实现有两种，根据字段数量和字段值大小自动选择：

  1. ZipList（压缩列表）：

    • 当 Hash 对象保存的所有键值对的键和值的字符串长度都小于 hash-max-ziplist-value（默认 64 字节），且键值对数量不超过 hash-max-ziplist-entries（默认 512）时，Hash 会使用 ZipList 作为底层实现。
    • 在 ZipList 中，字段（field）和值（value）作为两个连续的 entry 存储，结构紧凑，内存利用率高。

  2. Dict（字典）：

    • 当不满足上述 ZipList 条件时，Hash 会转换为 Dict（哈希表）实现。
    • Dict 提供了 O(1) 平均时间复杂度的查找、插入和删除操作，适合存储大量或大尺寸的键值对。

编码方式

Hash 对象的 encoding 属性可以是：

  • OBJ_ENCODING_ZIPLIST：使用 ZipList 编码。
  • OBJ_ENCODING_HT：使用 Dict（哈希表）编码。

Hash 的编码转换是双向的，但转换条件不对称：

  • ZipList → Dict：当 Hash 中的任意一个 field 或 value 的长度超过 hash-max-ziplist-value，或者 field-value 对的数量超过 hash-max-ziplist-entries 时，会从 ZipList 转换为 Dict。
  • Dict → ZipList：当删除元素后，如果 field 和 value 的长度都小于等于 hash-max-ziplist-value，且 field-value 对的数量小于等于 hash-max-ziplist-entries，不会自动转换回 ZipList。转换是单向的，一旦升级为 Dict，就不会再降级。

用户空间和内核空间

在操作系统中，进程的寻址空间被划分为用户空间和内核空间，这是为了保障系统的安全性和稳定性。

  • 内核空间：操作系统内核运行的特权模式区域，拥有对硬件和系统资源的完全访问权限。负责进程调度、内存管理、设备驱动、网络协议栈等核心功能。可以执行特权命令（Ring0），调用一切资源。
  • 用户空间：普通应用程序运行的非特权模式区域。应用程序无法直接访问硬件或执行特权指令，必须通过系统调用（System Call）向内核发起请求，由内核代为执行。只能执行受限命令（Ring3），不能直接调用系统资源。

Linux系统为了提高IO效率，会在用户空间和内核空间加入缓冲区：

当应用程序（如 Redis 服务器）需要进行网络 I/O、文件读写等操作时，必须经历“用户空间 → 内核空间 → 硬件 → 内核空间 → 用户空间”的数据拷贝过程。不同的 I/O 模型正是围绕如何高效地完成这一过程而设计的。

Linux五种IO模型

阻塞IO

阻塞IO（Blocking I/O） 是最简单的 I/O 模型。当应用程序发起一个 I/O 操作（如 read 系统调用读取网络数据）时，进程会一直等待，直到内核将数据准备好并拷贝到用户空间缓冲区。在两个阶段都必须阻塞等待，内核等待数据和从内核拷贝数据到用户空间，期间进程被挂起（阻塞），无法执行其他任务。

特点：

  • 同步、阻塞。
  • 实现简单，但并发性能差。每个连接需要一个线程/进程处理，大量连接时资源消耗巨大。
  • 在等待 I/O 完成期间，CPU 被闲置。

非阻塞IO

非阻塞IO（Non-blocking I/O） 通过将文件描述符设置为非阻塞模式来实现。当应用程序发起 I/O 操作时，如果数据尚未就绪，内核会立即返回一个错误（如 EAGAIN 或 EWOULDBLOCK），而不是让进程阻塞等待。在一阶段内核等待数据的时候是非阻塞的采用轮询（导致cpu使用率暴增），在二阶段阻塞等待内核拷贝数据。

特点：

  • 同步、非阻塞。
  • 应用程序需要不断轮询（polling）内核，检查数据是否就绪，这会导致 CPU 空转，浪费资源。
  • 虽然避免了进程阻塞，但轮询开销大，不适合高并发场景。

I/O 多路复用

I/O 多路复用（I/O Multiplexing） 是解决高并发 I/O 问题的核心模型。它允许一个进程/线程同时监视多个文件描述符（如多个 Socket 连接），并在其中任何一个就绪时得到通知。常见的系统调用有 select、poll、epoll（Linux）、kqueue（BSD/macOS）。进程反复调用recvfrom并等待返回成功标示（循环）。

  • select、poll只会通知用户进程有FD就绪，但不确定具体是哪个FD，需要用户进程逐个遍历FD来确认
  • epoll则会在通知用户进程FD就绪的同时，把已就绪的FD写入用户空间。

文件描述符（File Descriptior）：简称FD，是一个从0开始递增的无符号整数，用来关联Linux中的一个文件。在Linux中，一切皆文件，例如常规文件、视频、硬件设备等，当然也包括网络套字节（Socket）。

工作流程：

  1. 应用程序将需要监视的文件描述符集合注册到内核。
  2. 调用 epoll_wait 等函数阻塞等待，直到一个或多个文件描述符就绪。
  3. 内核通知应用程序哪些描述符就绪。
  4. 应用程序再对就绪的描述符进行非阻塞的读写操作。

特点：

  • 同步、阻塞在 multiplexer 上，但 I/O 操作本身是非阻塞的。
  • 单线程/进程即可处理大量并发连接，极大地提升了资源利用率。
  • Redis 采用的核心网络模型。

select

select 是 Unix/Linux 系统中最早出现的 I/O 多路复用系统调用，它允许一个进程同时监视多个文件描述符（FD），等待其中任何一个变为可读、可写或出现异常。

基本原理：

  1. FD 集合：select 使用三个位图（fd_set）结构分别表示需要监视的读、写和异常事件的文件描述符集合。
  2. 轮询检查：进程调用 select 时，会将这三个 fd_set 拷贝到内核空间。内核会遍历所有传入的 FD，检查它们的状态。如果有 FD 就绪（可读、可写或有异常），select 会返回，并修改 fd_set 来指示哪些 FD 就绪。
  3. 遍历确认：进程返回后，需要遍历整个 FD 集合（通过 FD_ISSET 宏）来找出具体哪些 FD 就绪，然后进行相应的 I/O 操作。

关键限制：

  • FD 数量限制：select 能监视的 FD 数量受 FD_SETSIZE 宏限制（通常为 1024）。这意味着单个进程最多只能同时监视 1024 个连接，不适合超高并发场景。
  • 性能问题：每次调用 select 都需要将整个 FD 集合从用户空间拷贝到内核空间，返回时再拷贝回来。同时，内核和用户进程都需要线性扫描整个 FD 集合来检查状态，时间复杂度为 O(N)。当连接数很大但活跃连接很少时，效率低下。
  • FD 集合重用：select 返回后会修改传入的 fd_set，因此每次调用前都需要重新设置（或使用备份）。

poll

poll 是 select 的改进版，它解决了 select 的一些设计缺陷，但核心模型相似。

基本原理：

  1. 事件结构体：poll 使用一个 pollfd 结构体数组来传递要监视的 FD 列表。每个 pollfd 结构体包含：
    • fd：文件描述符。
    • events：要监视的事件（如 POLLIN 表示可读）。
    • revents：返回时内核填充的就绪事件。
  2. 无数量硬限制：poll 没有 FD_SETSIZE 这样的硬编码限制，理论上能监视的 FD 数量仅受系统资源（如进程能打开的最大文件数）限制。
  3. 事件分离：events 和 revents 分离，避免了 select 中 fd_set 被内核修改后需要重置的问题。

仍然存在的问题：

  • 性能开销：和 select 一样，每次调用 poll 都需要将整个 pollfd 数组从用户空间拷贝到内核空间。内核仍需线性扫描所有 FD 来检查状态，返回后用户进程也需要遍历整个数组来找出就绪的 FD。时间复杂度仍是 O(N)。
  • 水平触发：poll 默认是水平触发（Level-Triggered，LT）模式。这意味着只要 FD 处于就绪状态（例如，接收缓冲区有数据可读），每次调用 poll 都会报告该 FD 就绪。如果应用程序没有一次性读完所有数据，下次调用 poll 时还会被通知，可能导致不必要的唤醒。

适用场景：相比 select，poll 更适合 FD 数量较多的场景，但其性能瓶颈在连接数非常大时依然明显。

epoll

epoll 是 Linux 2.6 内核引入的高性能 I/O 多路复用机制，专门为解决 select/poll 在大规模并发连接下的性能问题而设计。它是 Redis 在 Linux 上的首选多路复用器。

核心改进：

  1. 事件表（红黑树）：epoll 使用一个内核事件表（epoll_ctl 管理）来注册要监视的 FD，而不是每次调用都传递整个集合。这避免了每次调用时用户空间到内核空间的大量数据拷贝。
  2. 就绪列表（双向链表）：内核维护一个就绪列表，当某个 FD 就绪时，内核会通过回调函数将其加入到这个列表中。epoll_wait 调用时，只需检查这个就绪列表是否为空，不为空则直接返回就绪的 FD 信息。这使得检查就绪事件的时间复杂度从 O(N) 降为 O(1)。
  3. 边缘触发（ET）与水平触发（LT）：

    • 水平触发（LT LevelTriggered，默认）：只要 FD 处于就绪状态，每次 epoll_wait 都会报告它。
      内核维护该 fd 的就绪状态位。当 I/O 事件发生，fd 被加入就绪链表；epoll_wait 返回后，若用户未将缓冲区的数据全部读完，内核不会清除该 fd 的就绪状态位。下一次 epoll_wait 调用时，内核会再次将该 fd 放入就绪链表返回给用户。

      本质：只要缓冲区有数据（状态为“可读”），每次轮询都上报。
      缺陷：由于内核不会清除fd，每次fd就绪都会唤醒所有进程。

      • 边缘触发（ET EdgeTriggered）：只在 FD 状态发生变化时（例如，从不可读变为可读）报告一次。应用程序必须一次性处理完所有数据（循环读取直到返回 EAGAIN），否则可能丢失事件。ET 模式能减少系统调用次数，提高效率，但编程更复杂。

内核将 fd 的触发模式标记为一次性。当缓冲区从“空”变为“非空”（状态发生 0→1 的跳变）时，内核触发回调，将该 fd 放入就绪链表。epoll_wait 返回后，无论用户是否读完数据，内核立即将该 fd 从就绪链表中移除。除非缓冲区再次发生 0→1 的状态跳变（即先变空再变非空），否则该 fd 永远不会再出现在就绪链表中。
>本质：只上报状态变化的那一瞬间，且仅上报一次。
使用手动加回还有数据未读完的fd或者每一次通知使用非阻塞io读完缓冲区的数据， 避免LT模式可能的惊群现象。

  • 工作流程：
  1. 创建 epoll 实例：epoll_create 创建一个 epoll 句柄。
  2. 注册/修改/删除 FD：epoll_ctl 向 epoll 实例中添加、修改或删除要监视的 FD 及其关注的事件。
  3. 等待事件：epoll_wait 阻塞等待，直到有 FD 就绪，返回就绪的 FD 数组。

优势：

  • 高效：无需每次调用都传递 FD 集合，内核通过回调机制维护就绪列表，时间复杂度 O(1)。
  • 无 FD 数量限制：仅受系统最大文件描述符数限制。
  • 支持 ET 模式：可以减少不必要的唤醒，提高性能。

Redis 的选择：Redis 默认使用 epoll 的 LT 模式，因为它编程模型更简单，且 Redis 的事件处理循环能保证每次事件被触发后都及时处理。在 Linux 上，epoll 是支撑 Redis 高并发的关键技术之一。

对比总结：

因此，在现代高性能网络服务器（如 Redis、Nginx）中，epoll 已成为 Linux 平台上的事实标准。

web服务流程


整个流程分为 “准备阶段”、“内核监听阶段” 和 “事件分发处理阶段”。

第一阶段：启动与初始化（用户态准备）

Step 1：创建监听套接字（socket + bind + listen）

  • 底层动作：操作系统内核创建一个 struct socket 对象，并分配一个可用的文件描述符（比如 3）。该对象内部包含接收缓冲区（sk_rmem） 和发送缓冲区（sk_wmem）。
  • 状态：此时该 FD 处于 LISTEN 状态，等待客户端三次握手。

Step 2：创建 epoll 实例（epoll_create）

  • 底层动作：内核创建一个独立的 struct eventpoll 对象。这个对象里有两个核心结构：
    • 红黑树（rbr）：用于存放所有被监控的 FD（无论是否活跃）。
    • 就绪链表（rdllist）：用于存放触发了事件的活跃 FD。
  • 返回值：返回一个指向该实例的文件描述符（例如 epfd = 4）。

Step 3：注册监听事件（epoll_ctl 添加 ssfd）

  • 底层动作：将监听 FD（值为 3）添加到 epoll 实例（值为 4）的红黑树中。
  • 关键机制：内核会回调该 FD 对应的 poll 函数，将监听 FD 与 epoll 实例绑定。同时，在中断处理程序中注册回调函数（ep_poll_callback），告诉内核：“如果这个 FD 有读事件（新连接），请立马通知我。”

第二阶段：进程阻塞与内核等待（临界状态）

Step 4：进入事件循环（epoll_wait 阻塞）

  • 用户态动作：主线程调用 epoll_wait(epfd, events, MAX, -1)，其中 -1 表示无限等待，直到有事件发生。
  • 内核态动作（主动休眠）：
    1. 内核检查 eventpoll 对象的就绪链表（rdllist）。
    2. 如果链表为空，内核将当前进程（用户线程）的状态设置为 TASK_INTERRUPTIBLE（可中断睡眠），并将该进程加入到 epoll 实例的等待队列（wq） 中。
    3. 此时，CPU 被释放，该线程不再占用 CPU 资源，操作系统可以调度其他进程执行。

第三阶段：数据到达与唤醒（内核中断上下文）

Step 5：网卡中断与数据写入（硬件 -> 内核）

  • 底层动作：网卡接收数据，通过 DMA（直接内存访问） 将数据拷贝到内核内存的 Ring Buffer（环形缓冲区）中。
  • 触发中断：网卡发送硬中断，CPU 执行中断处理程序，根据数据包的 IP 和端口，找到对应的 struct socket 对象，将数据从网卡缓冲区拷贝到该 Socket 的接收缓冲区（sk_rmem）。

Step 6：执行 epoll 回调（ep_poll_callback）—— epoll 高性能的核心

  • 触发条件：当数据被成功写入接收缓冲区，且缓冲区状态由“空”变为“非空”（即状态发生变化）时，内核触发该 Socket 上注册的回调函数。
  • 回调执行的动作：
    1. 将当前触发的这个 FD（比如值为 3 的监听 FD）挂入 epoll 实例的就绪链表（rdllist） 尾部。
    2. 唤醒等待进程：检查 epoll 实例的等待队列（wq），发现之前有进程在 epoll_wait 上睡眠，立即将该进程状态设为 TASK_RUNNABLE（就绪态），并放入 CPU 的运行队列。

第四阶段：返回用户态与事件处理（业务分发）

Step 7：epoll_wait 返回就绪列表

  • 用户态动作：epoll_wait 系统调用从内核态返回。返回值 nfds 是就绪链表中 FD 的数量。
  • 数据拷贝：内核将就绪链表中的 FD 拷贝到用户态传入的 events 数组里。注意：此时只拷贝了 FD 和事件标志（如 EPOLLIN），并没有拷贝网络数据本身。

Step 8：遍历处理（核心逻辑分支）
用户线程开始遍历 events 数组，进行两步关键判断：

  • 分支 A：如果 fd == ssfd（监听套接字）—— 处理新连接

    • 调用 accept() 系统调用。
    • 内核执行：从监听 Socket 的全连接队列（已完成三次握手的队列）中取出第一个连接，创建一个新的 Socket 对象，分配一个新的文件描述符（例如 cfd = 5）。
    • 关键动作：立即调用 epoll_ctl(epfd, EPOLL_CTL_ADD, cfd, ...)，将新的客户端 FD 加入 epoll 的红黑树，并注册 EPOLLIN 事件，以便监听该客户端后续发送的请求数据。

  • 分支 B：如果 fd != ssfd（普通客户端 FD）—— 处理业务数据

    • 调用 read(fd, buf, len) 系统调用。
    • 内核执行：根据 FD 找到对应的 Socket 接收缓冲区，将数据从内核态拷贝到用户态的 buf 内存中（至此，数据才真正到达应用程序）。
    • 业务逻辑处理（解析 HTTP/JSON，查询数据库等）。
    • 调用 write(fd, resp, len)，将响应数据从用户态拷贝回内核的 Socket 发送缓冲区，由内核协议栈打包发回客户端。

第五阶段：细节与闭环（边缘情况）

Step 9：水平触发（LT）与边缘触发（ET）的底层差异

  • 若设置为 LT（默认）：只要 Socket 接收缓冲区还有数据没读完，内核每次检查就绪链表时，都会将对应的 FD 重新放回链表（除非用户手动epoll_ctl MOD去掉），确保下次 epoll_wait 还会返回。
  • 若设置为 ET：回调触发一次后，该 FD 会被立即从就绪链表中移除。即使缓冲区还有残留数据，只要没有新的数据包触发“空 -> 非空”的状态变化，该 FD 再也不会出现在就绪链表中。

Step 10：循环回写与关闭

  • 处理完所有就绪的 events 后，回到 while 循环顶部，再次调用 epoll_wait。
  • 如果客户端关闭连接，内核会触发 EPOLLHUP 或 EPOLLERR 事件，业务层需要捕获并调用 close(fd) 释放资源，同时调用 epoll_ctl(epfd, EPOLL_CTL_DEL, fd, NULL) 将 FD 从红黑树中删除。

总结

  • ssfd 通过socket + bind + listen诞生，并带着空的全连接队列进入 epoll 红黑树。当客户端三次握手完成，内核将连接对象放入 ssfd 的全连接队列，触发EPOLLIN事件。

  • epoll_wait 返回后，进入分支判断：

    • 如果 fd == ssfd（监听套接字，只处理连接）：说明有新连接来了，此时调用 accept()，从 ssfd 的全连接队列里“拽”出连接对象，贴上一个新编号 cfd（客户端套接字）。

    • 如果 fd != ssfd（即普通客户端套接字 cfd，处理客户端发来的业务请求数据）：说明是业务数据到了，此时调用 read() 处理请求。

    • EPOLLHUP（对方关闭连接）：此时调用 read 会返回 0，你应该关闭这个 FD。

EPOLLERR（连接异常）：此时需要做清理工作所以这个也是发生在cfd而不是ssfd的时候吗

  • 拿到 cfd 后，必须手动执行 epoll_ctl(ADD, cfd)，把这个新编号也塞进 epoll 红黑树，它才能开始监听后续的业务数据。

信号驱动IO

信号驱动IO（Signal-driven I/O） 允许进程在文件描述符就绪时接收一个信号（SIGIO），从而避免轮询。进程首先开启信号驱动 I/O，然后可以继续执行其他任务。当数据就绪时，内核会发送一个信号通知进程，进程再执行 I/O 操作。

特点：

  • 异步通知，但 I/O 操作本身仍是同步的（数据拷贝阶段进程仍需等待）。
  • 避免了轮询，但信号处理复杂，且信号队列可能溢出，不适合高性能网络服务器。

异步IO

异步IO（Asynchronous I/O，AIO） 是最彻底的异步模型。应用程序发起一个 I/O 请求后立即返回，可以继续处理其他任务。内核负责完成整个 I/O 操作（包括数据准备和从内核空间到用户空间的拷贝），完成后通过回调函数、信号或事件通知应用程序。

特点：

  • 真正的异步，从发起请求到数据就绪的整个过程都不阻塞应用程序。
  • 性能理论上最优，但编程模型复杂，且在不同操作系统上支持程度不一（Linux 的 AIO 实现并不完善）。
  • 高并发需要限流，否则可能导致内存占用过多而崩溃

同步异步

IO操作时同步还是异步，关键看数据在内核空间与用户空间的拷贝过程（数据读写的IO操作），也就是阶段二时同步还是异步。

  • 如果是用户线程调用的 read，阻塞 => 同步I/O（epoll、select、非阻塞轮询都是这个范畴）。

  • 如果是内核主动拷贝并通知，用户线程没有调用 read => 异步I/O（io_uring、IOCP）。

Redis网络模型

Redis 4.0 的多线程 (后台任务) ：

  • 引入了多线程异步处理一些耗时较长的任务，例如异步删除命令unlink。

Redis 6.0 的多线程（网络 I/O）：

  • 为了应对网络 I/O 成为瓶颈的场景（如高带宽、大响应），Redis 6.0 引入了多线程 I/O（默认关闭，需配置 io-threads 和 io-threads-do-reads）。
  • 注意：多线程仅用于网络数据的读取（read）和发送（write），而命令的解析和执行依然在单线程中进行。这避免了多线程并发访问数据结构的复杂性，保持了 Redis 单线程执行命令的原子性优势。
  • 主线程仍然负责监听事件和分发任务，将就绪的读/写操作交给 I/O 线程池并行处理，处理完毕后再交回主线程进行命令解析或结果返回。

总结：Redis 通过 单线程 Reactor + I/O 多路复用 的核心架构，在保证命令原子性和简化内部实现的同时，实现了极高的并发性能。其网络模型是理解 Redis 高性能的关键。

Redis 的网络模型基于 Reactor 模式，并高度依赖 I/O 多路复用 技术。

  1. 单线程事件循环（Event Loop）：Redis 的主线程运行一个事件循环，负责监听所有客户端连接的文件描述符。
  2. I/O 多路复用器：在 Linux 上优先使用 epoll，在 BSD/macOS 上使用 kqueue，在其他系统上使用 select 作为备选。这使得单个线程可以高效地管理数万甚至数十万的并发连接。
  3. 事件分发与处理：
    • 连接事件：当有新连接到来时，事件循环接受连接，创建客户端对象，并将其读事件注册到多路复用器。
    • 读事件：当客户端发送命令数据时，内核通知事件循环，主线程读取命令、解析协议（RESP）、执行命令。
    • 写事件：命令执行完毕后，将响应数据写入客户端的输出缓冲区，并注册写事件。当套接字可写时，将缓冲区数据发送给客户端。
  4. 时间事件：事件循环还会处理定时任务（如 serverCron 函数），用于键过期、持久化、统计等后台操作。

1. 为什么Redis要选择单线程？

  • 抛开持久化不谈，Redis是纯内存操作，执行速度非常快，它的性能瓶颈是网络延迟而不是执行速度，因此多线程并不会带来巨大的性能提升。

  • 多线程会导致过多的上下文切换，带来不必要的开销。

  • 引入多线程会面临线程安全问题，必然要引入线程锁这样的安全手段，实现复杂度增高，而且性能也会大打折扣。

  • 原子性：每个命令的执行都是原子的，这简化了数据一致性的处理。

  • 可预测的性能：操作是顺序执行的，延迟稳定。

单线程的瓶颈：CPU 不是 Redis 的瓶颈，因为大多数操作都是内存访问，速度极快。瓶颈往往在网络 I/O 或内存访问速度上。对于耗时的命令（如 KEYS *、FLUSHALL），会阻塞整个线程，导致其他请求延迟。

为了缓解这个问题，Redis 6.0 引入了多线程 I/O（默认关闭）。注意，这并非多线程处理命令，而是让额外的线程专门负责网络数据的读取（read）和发送（write），而命令的解析和执行依然由主线程完成。这可以有效提升网络吞吐量，尤其是在高带宽场景下。

通信协议

Redis 使用自定义的 RESP（REdis Serialization Protocol） 协议进行客户端与服务端之间的通信。它设计简单、高效、可读性强（人类可读），并且易于实现。

RESP 通过第一个字节来标识数据的类型：

  • 简单字符串（Simple Strings）：以 + 开头，后跟字符串内容，以 \r\n 结尾。例如：+OK\r\n。
  • 错误（Errors）：以 - 开头，格式与简单字符串类似，但表示错误信息。例如：-ERR unknown command 'foobar'\r\n。
  • 整数（Integers）：以 : 开头，后跟整数字符串，以 \r\n 结尾。例如：:1000\r\n。
  • 批量字符串（Bulk Strings）：以 $ 开头，后跟字符串的字节长度，然后是 \r\n，再然后是实际的字符串数据，最后以 \r\n 结尾。用于传输二进制安全的字符串。例如：$6\r\nfoobar\r\n。空字符串表示为 $0\r\n\r\n，Null 值表示为 $-1\r\n。
  • 数组（Arrays）：以 * 开头，后跟数组的元素个数，然后是各元素自身的 RESP 格式。客户端发送的命令就是数组格式。例如，命令 SET key value 被编码为 *3\r\n$3\r\nSET\r\n$3\r\nkey\r\n$5\r\nvalue\r\n。

通信流程示例（SET/GET）：

  1. 客户端发送：*3\r\n$3\r\nSET\r\n$3\r\nkey\r\n$5\r\nvalue\r\n
  2. 服务端回复：+OK\r\n
  3. 客户端发送：*2\r\n$3\r\nGET\r\n$3\r\nkey\r\n
  4. 服务端回复：$5\r\nvalue\r\n

这种协议设计使得 Redis 客户端的实现非常简单，并且可以通过 telnet 或 nc 工具直接与 Redis 服务器进行交互。

内存策略

Redis 作为内存数据库，高效的内存管理至关重要。它采用了多种策略来优化内存使用。

内存分配器

Redis 默认使用 jemalloc 作为内存分配器（也可以选择 libc 或 tcmalloc）。jemalloc 在减少内存碎片方面表现优异，它通过分配不同大小的内存区域（arena）来管理内存，能更好地满足 Redis 频繁分配和释放小对象的需求。

过期策略-DB结构

Redis 的键过期功能依赖于其数据库（DB）层面的特殊数据结构来高效地管理和触发过期事件。每个 Redis 数据库（默认 16 个，编号 0-15）内部维护了两个核心字典（Dict）和一个“过期键”专用字典。

1. 核心数据结构：redisDb

每个 Redis 数据库由一个 redisDb 结构体表示，其简化定义如下：

我们重点关注前两个字典：

  • dict（键空间）：存储该数据库中所有的键值对。键是字符串对象，值可以是任意 Redis 对象（String、List、Hash 等）。
  • expires（过期字典）：存储所有设置了过期时间（TTL）的键及其对应的过期时间戳（以毫秒为单位的 UNIX 时间戳）。

2. 过期字典 (expires) 的工作原理

过期字典是一个标准的 Redis 字典（哈希表），其键（Key）与键空间（dict）中的键共享同一个 SDS 字符串对象（通过引用计数管理），值（Value）是一个 long long 类型的整数，表示该键的绝对过期时间戳（毫秒精度）。

示例：

  • 执行 SET user:1000 "Alice" EX 60 命令后：
    1. 在 dict 中插入键 "user:1000"，值指向字符串对象 "Alice"。
    2. 在 expires 中插入键 "user:1000"，值为 (current_time + 60000)（当前时间戳 + 60 秒对应的毫秒数）。

3. 过期键的判定与删除流程

Redis 通过结合 惰性删除 和 定期删除 两种策略来清理过期键，两者都依赖 expires 字典。

惰性删除（Lazy Expiration）

  • 触发时机：在任何命令访问某个键时（如 GET、HGET、LRANGE 等）。
  • 执行流程：
    1. 命令实现代码在执行前，会调用 expireIfNeeded(redisDb *db, robj *key) 函数。
    2. 该函数检查 expires 字典中是否存在该键。
    3. 如果存在，则比较当前时间与字典中存储的过期时间戳。
    4. 如果已过期，则同步删除该键（从 dict 和 expires 中移除，释放内存），然后返回键不存在的状态给客户端。
    5. 如果未过期或未设置过期，则继续执行原命令。
  • 优点：对 CPU 友好，只在访问时付出额外开销。
  • 缺点：如果某个键永不被访问，即使已过期也会一直占用内存，造成内存泄漏。因此需要定期删除作为补充。

定期删除（Active Expiration）

SLOW 模式：

  • 触发时机：由 Redis 的时间事件处理器 serverCron（默认每 100ms 执行一次）周期性触发。
  • 执行流程（简化）：
    1. 每次 serverCron 运行时，会遍历各个数据库。
    2. 从 expires 字典中随机抽取一定数量的键（默认 ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP 为 20）。
    3. 检查每个被抽中的键是否过期，如果过期则删除。
    4. 如果本轮抽查中过期键的比例超过 25%，则重复步骤 2-3，直到过期键比例低于 25% 或达到时间限制（默认 25ms），防止阻塞主线程太久。切下一个库Redis，SLOW 跑完后，Redis 会统计全局预估过期键占比 server.stat_expired_stale_perc，>10% 才会在 beforeSleep 执行 FAST。
  • 优点：限制了执行时长和频率，减少了对正常服务的影响，并清理了那些不被访问的过期键。
  • 缺点：是概率性清理，无法保证所有过期键被立即删除。

FAST模式

  • 调用入口：beforeSleep() —— 这个函数在 每次事件循环（aeMain）进入阻塞 epoll_wait 之前都会被执行。

  • 核心目标：在处理新到达的客户端请求之前，尽可能释放当前已过期的 Key，避免请求处理过程中频繁触发惰性删除（Lazy Expiration）带来的延迟毛刺。

  • 执行逻辑（与 SLOW 的硬区别）：

  1. 时间限制极严：执行时长硬上限仅为 1ms（而不是 SLOW 的 25ms）。
  2. 频率限制：如果距离上一次 FAST 模式执行不到 2ms，则本次直接跳过（防止频繁执行浪费 CPU）。
  3. 扫描策略：不会从 DB 0 开始重新扫，而是接着 SLOW 模式上次未扫完的数据库进度继续扫（共享迭代游标）。
  4. 终止条件：只要扫描到的过期 Key 数量超过 1 0%且没达到时间上限就继续，立即停止循环。

4. 过期信息的持久化

为了在 Redis 重启后能恢复键的过期状态，expires 字典中的信息也需要被持久化：

  • RDB 持久化：
    • 生成 RDB 文件时，会保存每个设置了过期时间的键及其剩余的生存时间（TTL，秒级精度）。
    • 加载 RDB 文件时，会根据保存的 TTL 重新计算绝对时间戳并写入 expires 字典。
  • AOF 持久化：
    • AOF 文件记录的是写命令。当某个键因过期被惰性删除或定期删除时，Redis 会向 AOF 文件追加一条 DEL 命令。
    • 在 AOF 重写（Rewrite）时，会检查键的过期时间，如果已过期则不会写入新 AOF 文件。

内存淘汰策略

当内存使用达到 maxmemory 配置的阈值时，Redis 会根据 maxmemory-policy 配置的策略来淘汰数据，以腾出空间写入新数据。Redis会在处理客户端命令的方法processCommand()中尝试做内存淘汰。常见策略有：

  • noeviction：不淘汰，新写入操作会报错。（默认策略）
  • volatile-ttl：从设置了过期时间的键中，移除剩余生存时间最短的键。
  • allkeys-random：从所有键中，随机移除某个键。
  • volatile-random：从设置了过期时间的键中，随机移除某个键。
  • allkeys-lru：从所有键中，移除最近最少使用的键。
  • volatile-lru：从设置了过期时间的键中，移除最近最少使用的键。
  • allkeys-lfu：从所有键中，移除最少频率使用的键。
  • volatile-lfu：从设置了过期时间的键中，移除最少频率使用的键。

    LRU(Least Recently Used)，最少最近使用。当前时间减去最后一次访问时间，越大淘汰优先级越高。
    LFU(Least Frequently Used)，最少频率使用。统计每个key访问频率，越小淘汰优先级越高。

对象系统与引用计数

Redis 的所有键值对都是用“Redis 对象”来表示的。每个对象由一个 redisObject 结构表示：

  • 引用计数（refcount）：用于实现内存回收。当创建一个对象时，refcount 被初始化为 1。当对象被一个新程序使用时，计数加 1；不再被使用时，计数减 1。当计数为 0 时，对象所占用的内存会被释放。这也使得多个键可以共享同一个值对象，节约内存。
  • LRU 字段：记录对象最后一次被访问的时间戳（或近似空转时长），用于在内存不足时进行淘汰。
  • LFU 字段：逻辑访问次数：
    1. 生成0~1之间的随机数R
    2. 计算1/（就次数 * lfu_log_factor + 1），记录为P，lfu_log_factor默认为10
    3. 如果R < P，则计数器+1，且最大不超过255
    4. 访问次数会随时间衰减，距离上一次访问时间每隔lfu_decay_time分钟（默认1），计数器+1

总结

初始化空的 eviction_pool 淘汰候选池，根据当前淘汰策略，计算每个 key 的 idleTime，不管 LRU/LFU/TTL 用什么公式算出 idleTime，最终统一规则：idleTime 越小，越优先淘汰；候选池全部按 idleTime 升序存储，从 eviction_pool 倒序取出 idleTime 最小的 key（最应该淘汰的 key）执行删除

内存优化技巧

  1. 使用适当的数据类型：例如，存储小数字用 String 的 int 编码，存储短的字符串用 embstr 编码的 String，存储多个字段用 Hash 的 ziplist 编码（在元素少时）。
  2. 使用 Bitmaps、HyperLogLogs：用于特定场景（如统计活跃用户、基数估算）可以极大节省内存。
  3. 控制键的数量：过多的键本身就会带来元数据开销。可以使用 Hash 类型将多个相关字段聚合到一个键中。
  4. 使用 32 位实例：如果内存不超过 4GB，可以考虑使用 32 位编译的 Redis，指针占用空间更小。
  5. 监控内存碎片率：通过 INFO memory 命令关注 mem_fragmentation_ratio。如果比率持续很高（如 > 1.5），可以考虑重启 Redis 实例来重整内存（在从节点或低峰期进行）。
