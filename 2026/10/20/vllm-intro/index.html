前言

当我们希望把一个开源模型部署为对外服务时，最先想到的往往是使用 HuggingFace 的 transformers 库加载模型，再对外提供 HTTP 接口。而在不增加 GPU 的前提下想要提升模型性能，vLLM 就充当了这样一个中间层——它位于大模型与硬件之间，帮助模型更充分地利用显存与算力。它的使用方式也非常简单，只需一行 vllm serve 命令，即可提供与 OpenAI 接口一致的服务。

KV cache

Q、K、V

在讲 KV cache 之前，先把注意力机制里的 Q、K、V 说清楚，后面的一切都建立在这三个向量之上。

Transformer 的注意力计算可以类比成一次「检索」：

  • Q（Query，查询）：当前 token 想「问」什么。它代表当前位置的检索意图。
  • K（Key，键）：每个 token 对外提供的「标签」，用来和 Q 做匹配，衡量彼此的相关程度。
  • V（Value，值）：每个 token 真正携带的「内容」，匹配度越高，它的内容被采纳得越多。

计算过程也很直观：用当前 token 的 Q 与所有 token 的 K 做点积得到注意力分数，经 softmax 归一化成权重，再对所有 token 的 V 加权求和，就得到当前位置的输出。写成公式即：

$$ \text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^\top}{\sqrt{d_k}}\right)V $$

其中 $d_k$ 是 Key 向量的维度，除以 $\sqrt{d_k}$ 是为了防止点积结果过大导致 softmax 梯度消失。

关键点在于：K 和 V 只由对应位置的 token 决定，一旦算出来就不会再变。生成第 N 个 token 时，前 N-1 个 token 的 K、V 与上一步完全相同，重复计算纯属浪费——这正是 KV cache 存在的理由。

为什么需要 KV cache

大模型生成文本是「一个词一个词往外蹦」的：每生成一个新 token，都要把「已有的全部 token」重新送进模型算一遍注意力。而注意力计算里，每个 token 都会产生一对 Key 和 Value 向量。如果不做缓存，第 N 步就要把前 N-1 步的 K、V 全部重算一遍，计算量随序列长度呈平方级增长，显存带宽也被反复浪费。

KV cache 的思路很朴素：把已经算过的 K、V 存起来，下一步直接复用。这样每生成一个 token，只需为新 token 计算一次 K、V，再与历史缓存做注意力即可，把重复计算降为一次。代价是缓存本身要占显存——序列越长、并发越多，KV cache 越大，它往往才是推理服务里真正的显存瓶颈。

PagedAttention：像操作系统管理内存一样管理 KV cache

传统实现里，KV cache 通常要求为每条请求预留一段连续显存，并按最大长度分配。问题很明显：

  • 实际生成长度往往远小于最大长度，预留的空间大量闲置（内部碎片）；
  • 不同请求长度不一，连续分配容易产生外部碎片；
  • 请求结束后空间难以被其他请求复用，显存利用率低。

vLLM 提出的 PagedAttention 借鉴了操作系统的虚拟内存分页机制：把 KV cache 切成固定大小的 block（页），每个 block 存放固定数量 token 的 K、V。每条请求维护一张「逻辑块 → 物理块」的映射表，物理块在显存中无需连续，按需分配、用完即还。

这样一来：

  • 显存按需分配，几乎消除内部碎片，实测可将 KV cache 的显存浪费压到极低；
  • 不同请求的物理块可以灵活复用，支持更高的并发吞吐；
  • 相同前缀的请求还能共享物理块，这正是 prefix caching（前缀缓存）的基础。

一句话概括：PagedAttention 让 KV cache 从「整块预留」变成「按页调度」，从而把显存用得更满、把并发做得更高。

vLLM 中与 KV cache 相关的关键启动参数

参数 默认值 说明
--block-size 16 每个 KV cache block 容纳的 token 数。取值越小，碎片越少但映射开销越大；一般保持默认即可。
--swap-space 4（GiB/卡） 每张 GPU 可用于把被换出的 KV cache 暂存到 CPU 内存的空间大小，显存吃紧时用于腾挪。
--enable-prefix-caching 关闭 开启前缀缓存，多个请求共享相同前缀的 KV block，显著加速系统提示词、few-shot 示例等重复前缀场景。
--gpu-memory-utilization 0.9 单卡显存占用比例，vLLM 会把其中一部分划给 KV cache，调大可容纳更多并发与更长上下文。
--max-model-len 模型默认 单条请求的最大上下文长度，直接决定单请求 KV cache 的上限。
--max-num-seqs 自动 单批次最大并发请求数，并发越高 KV cache 占用越大，需与显存容量匹配。

批处理与调度器

有了 PagedAttention 把显存管好，vLLM 还需要一套机制来决定「同一时刻让哪些请求一起算、按什么顺序算」，这就是调度器（Scheduler）与批处理（Batching）要解决的问题。

从静态批处理到连续批处理

最朴素的做法是静态批处理：攒够一批请求，一起送进 GPU，等这一批里最长的请求生成完，再整批返回、开始下一批。问题在于大模型的输出长度差异极大——同一批里若有一条请求生成了 2000 个 token，其余只生成 20 个 token 的请求也只能干等着，GPU 在等待期间几乎空转。

vLLM 采用的是连续批处理（Continuous Batching），也叫迭代级调度（iteration-level scheduling）：调度不再以「一整批请求」为粒度，而是以「一次前向迭代」为粒度。每生成一个 token 后，调度器都会重新检查队列：

  • 有请求生成结束（遇到 EOS 或达到 max_tokens），立刻把它移出批次，释放其占用的 KV block；
  • 有新请求到达，只要显存还放得下它的 KV cache，就立刻插进当前批次一起计算。

这样 GPU 的每个迭代都尽可能被填满，长请求不会拖住短请求，短请求也不会占着位置空等，整体吞吐和平均延迟都明显改善。

这里需要澄清两个容易混淆的点：什么是一次前向迭代，以及为什么它和静态批处理不是一回事。

先说「一次前向迭代」。大模型推理时，每调用一次模型、让数据在 GPU 上完整地流过一遍所有层，就叫一次前向迭代（forward iteration）。一次迭代的产出是：批次里每条请求各自的下一个 token（prefill 阶段则是整段 prompt 的 KV cache）。所以「一次迭代」是 GPU 计算的最小调度单位，它对应一次 kernel 调用序列，而不是「一条请求从头生成到尾」。

关键区别就在这里：静态批处理以「一整批请求的生命周期」为粒度，连续批处理以「一次前向迭代」为粒度。

  • 静态批处理：一批请求一起进来，必须等这批里最长的请求把全部 token 生成完，整批才算结束，期间哪怕别的请求早就生成完了，它们占的位置也不能让给新请求。批次成员在整个生命周期内固定不变。
  • 连续批处理：每跑完一次前向迭代，调度器就重新组一次批。某条请求在这一轮里生成了 EOS，下一轮它就不在批次里了，它腾出的 KV block 立刻可以给新请求用；新请求到达后，下一轮就能被塞进来一起算。

所以「一次前向迭代」和「一次完整的 prefill」完全是两个尺度。一条带 3000 token 长 prompt 的请求，它的 prefill 在默认配置下确实是在一次前向迭代里算完的——这一次迭代很重，但它只是一次迭代，算完就结束了，下一轮迭代调度器立刻可以重新组批，把这条请求转入 decode，同时把新请求加进来。而静态批处理要等的是这条请求把回答全部生成完（可能几百上千次迭代），两者等待的时长差了几个数量级。

换句话说，连续批处理的「连续」体现在：批次不是一次性锁定到请求结束，而是每轮迭代都可以换人。哪怕某一轮迭代因为长 prefill 而变慢，它也只是「这一轮慢」，不会像静态批处理那样让整批请求陪着一条长请求耗到它彻底结束。

下面这张图对比了静态批处理与连续批处理在时间轴上的差异：

flowchart TD
  subgraph S["静态批处理"]
    S1["请求 A、B、C 同时进入"] --> S2["等待最长的请求 C 生成完毕"]
    S2 --> S3["整批一起返回，期间空位无法复用"]
  end
  subgraph C["连续批处理"]
    C1["每轮迭代后重新组批"] --> C2["请求 B 生成结束，立即移出并释放 KV block"]
    C2 --> C3["新请求 D 下一轮即可插入"]
    C3 --> C1
  end

调度器的基本流程

vLLM 的调度器在每一轮迭代中大致做三件事：

  1. 挑请求：按先来先服务（FCFS）等策略从等待队列（waiting）中取出请求，判断其所需 KV block 能否分配；
  2. 分块：为被选中的请求分配物理 block，若显存不足则触发抢占（preemption）；
  3. 组批：把本轮要计算的请求组成一个 batch，交给模型执行前向计算。

其中「分块」这一步正是 PagedAttention 的用武之地——因为 KV cache 按页管理，调度器可以精确地知道「还能塞下几个 token 的缓存」，从而做出更细粒度的准入决策。

需要强调的是，调度器是在每轮迭代之间重新组批的：一次前向迭代一旦提交给 GPU，批次里所有请求就必须一起算完，这一轮的耗时由批次里最重的活决定，调度器无法在迭代执行到一半时把请求「踢出去」。因此「每轮迭代换人」只解决了批次成员多久更新一次，并没有解决单轮迭代内部负载不均——如果某一轮迭代里塞进了一个 3000 token 的 prefill，这一轮的计算量就是几十上百个 decode 步骤的量级，同批次里那些只需算一个 token 的 decode 请求，仍然要在这一轮里陪着等，用户看到的就是输出一顿一顿、延迟抖动明显。这正是下一节「分块 prefill」要解决的问题。

调度器在一轮迭代中的处理流程可以概括为：

flowchart TD
  A["等待队列 waiting"] --> B{"所需 KV block 能否分配"}
  B -- "能" --> C["分配物理 block"]
  B -- "不能" --> D["触发抢占 preemption"]
  D --> E["换出 Swap 或 重算 Recompute"]
  E --> C
  C --> F["组成本轮 batch"]
  F --> G["交给模型执行前向计算"]
  G --> A

抢占：显存不够时怎么办

当新请求或正在运行的请求需要更多 KV block，而显存已经分配完时，调度器必须抢占一部分请求来腾出空间。vLLM 提供两种回收方式：

  • 换出（Swap）：把被抢占请求的 KV block 拷贝到 CPU 内存（即 --swap-space 指定的空间），等它重新被调度时再拷回 GPU；
  • 重算（Recompute）：直接丢弃该请求的 KV cache，等它恢复运行时，把已有的 token 重新做一次 prefill 把缓存算回来。

一般来说，换出的代价是 PCIe 带宽，重算的代价是算力，调度器会根据请求长度和当前负载选择更划算的一种。这也解释了为什么 --swap-space 和 --max-num-seqs 需要一起调：前者决定了能「暂存」多少，后者决定了同时「在跑」多少。

与调度相关的常用参数

参数 默认值 说明
--max-num-seqs 自动 单批次最大并发序列数。调大可提升吞吐，但 KV cache 占用随之上升。
--max-num-batched-tokens 自动 单次迭代最多处理的 token 数（含 prefill 与 decode），是控制单步计算量的关键旋钮。
--swap-space 4（GiB/卡） 被抢占请求的 KV cache 可换出到 CPU 内存的空间上限。
--scheduler-policy fcfs 调度策略，先来先服务；部分版本还支持优先级调度。
--enable-chunked-prefill 关闭 开启分块 prefill，把长 prompt 的 prefill 拆成多轮，避免长请求阻塞正在 decode 的请求。

一个开启分块 prefill 的启动示例

长 prompt 场景下，单次 prefill 可能占用大量计算时间，导致同批次里正在逐 token 生成的请求被「卡住」。要理解这句话，先分清推理中的两个阶段：

  • prefill（预填充）：把用户输入的整段 prompt 一次性送进模型，算出所有 token 的 KV cache。这是一次「大批量计算」，prompt 越长，耗时越久。
  • decode（解码）：逐 token 生成回答，每步只算一个新 token，单步计算量很小。

开启分块 prefill 后，长 prompt 的 prefill 不再一口气算完，而是按 --max-num-batched-tokens 的预算拆成若干块，每轮迭代只算一块，剩余预算留给 decode 请求，两者交替执行。于是每轮迭代的计算量被控制在相近水平，decode 请求不会被长时间阻塞，长 prompt 的首 token 延迟也更平滑、可预测：

需要说明的是，--max-num-batched-tokens 调大能提升单步吞吐，但会拉长单次迭代耗时，进而影响交互式场景的响应速度；调小则相反。实际部署时建议先用默认值压测，再结合业务的「吞吐优先」还是「延迟优先」逐步调整。

量化

为什么需要量化

前面几节讨论的都是「怎么把显存用得更满、把请求排得更顺」，但有一个更根本的约束始终存在：模型权重本身就要占显存。一个 7B 参数的模型，用 FP16 存储大约需要 14 GB 显存，再加上 KV cache 和中间激活，单卡 24 GB 往往只能勉强跑起来；70B 级别的模型更是需要多卡才能装下。

量化（Quantization）的思路是：用更低的数值精度来表示权重和激活，把 FP16 的 16 bit 压缩到 8 bit（FP8）、4 bit 甚至更低。带来的收益很直接：

  • 显存占用大幅下降：4 bit 量化后，7B 模型的权重只需约 4 GB，原本装不下的模型变得可以单卡部署；
  • 显存带宽压力减小：decode 阶段是典型的「访存瓶颈」，每生成一个 token 都要把权重从显存读一遍，权重变小意味着读得更快，吞吐随之提升；
  • 单位显存能容纳更多并发：权重省下来的显存可以留给 KV cache，从而支撑更大的 batch。

代价则是精度损失——量化越激进，模型输出质量下降的风险越大，需要在「省显存」和「保效果」之间权衡。

常见的量化方案

按「量化发生在什么时候」，可以粗略分成两类：

  • 训练后量化（PTQ，Post-Training Quantization）：模型训练完成后，用少量校准数据统计权重/激活的分布，直接算出量化参数。成本低、落地快，是推理部署中最常用的方式，GPTQ、AWQ 都属于这一类。
  • 量化感知训练（QAT，Quantization-Aware Training）：在训练过程中模拟量化误差，让模型提前「适应」低精度，通常精度更好，但需要重新训练，成本高得多。

按「量化对象」又可以分成：

  • 仅权重量化（Weight-Only）：只把权重压到 INT8/INT4，激活仍保持 FP16。实现简单、兼容性好，是当前主流做法；
  • 权重 + 激活量化（W8A8 等）：权重和激活都用低精度，能进一步利用 INT8 矩阵乘的算力，但对校准和算子支持要求更高。

几个常见的具体算法：

方案 特点 适用场景
GPTQ 逐层做二阶误差补偿，4 bit 下效果稳定，生态成熟 通用 GPU 推理，社区量化模型最多
AWQ 依据激活分布识别「重要通道」并加以保护，4 bit 精度通常优于 GPTQ 对精度要求较高的场景
FP8 直接使用 FP8 数据类型，无需复杂校准，Hopper 及更新架构原生支持 新卡上的高吞吐推理
INT8（W8A8） 权重与激活均为 INT8，可利用 INT8 Tensor Core 追求极致吞吐、对精度容忍度较高

常用参数说明：

  • --quantization：量化方式，常见取值有 awq、gptq、fp8、bitsandbytes 等；不指定时由模型配置自动推断。
  • --dtype：非量化部分（如激活、KV cache）的数据类型，通常保持 auto 或 float16/bfloat16。
  • --kv-cache-dtype：KV cache 的数据类型，设为 fp8 可以把 KV cache 也压到 8 bit，进一步缓解显存压力，但需要硬件支持。

量化与 KV cache 的关系

需要特别区分两个容易混淆的概念：权重量化和 KV cache 量化是两件独立的事。

  • 权重量化（GPTQ/AWQ 等）压缩的是模型参数，影响的是「模型本身占多少显存」；
  • KV cache 量化（--kv-cache-dtype fp8）压缩的是推理过程中缓存的 K、V，影响的是「能同时服务多少请求、支持多长上下文」。

两者可以叠加使用：先用 AWQ 把权重压到 4 bit，再用 FP8 压缩 KV cache，显存利用率可以再上一个台阶。不过 KV cache 量化对精度的影响通常比权重量化更敏感，建议在压测中对比开启前后的输出质量再决定。

下图展示了权重量化与 KV cache 量化分别作用于推理链路的哪个环节：

flowchart LR
  A["模型权重 FP16"] -- "权重量化 GPTQ / AWQ / FP8" --> B["低精度权重 INT4 / FP8"]
  C["KV cache FP16"] -- "KV cache 量化 --kv-cache-dtype fp8" --> D["低精度 KV cache FP8"]
  B --> E["显存占用下降"]
  D --> F["并发与上下文容量提升"]

实践建议

  • 优先选社区验证过的量化模型：AWQ / GPTQ 的 4 bit 版本在多数任务上与原模型差距很小，直接拿来用最省事；
  • 先量化权重，再考虑 KV cache：权重是显存占用的「大头」，收益最明显；KV cache 量化留作进一步优化的手段；
  • 量化后务必回归测试：用业务真实数据对比量化前后的输出，重点关注长文本、代码、数学等对精度敏感的任务；
  • 注意硬件与算子支持：FP8 需要较新的 GPU 架构，部分量化方式在特定卡型上可能没有高效 kernel，实际吞吐未必如预期。

一句话概括：量化是在「显存」和「精度」之间做交换，vLLM 负责把量化后的模型跑得又快又稳，而选哪种量化方案、压到什么程度，取决于你的显存预算和业务对效果的容忍度。

GPU worker

下面这张图展示了从请求进入到 token 回传的完整链路：

flowchart TD
  A["客户端请求"] --> B["API Server<br/>接收 HTTP 请求 / tokenize"]
  B --> C["Engine Core 调度器<br/>挑请求 · 分配 KV block · 组批"]
  C --> D["下发执行计划<br/>请求列表 + block table + 本轮 token 数"]
  D --> E["GPU worker<br/>准备输入张量"]
  E --> F["执行前向计算<br/>PagedAttention 读写 KV cache"]
  F --> G["采样得到下一个 token"]
  G --> H["回传 token 与 KV cache 状态"]
  H --> C
  C --> I["API Server 返回响应"]

图注：API Server 负责接收请求与 tokenize，把请求交给 Engine Core；Engine Core 中的调度器决定本轮算哪些请求、分配 KV block 并组批，再把执行计划下发给 GPU worker；worker 持有模型权重与 KV cache 物理显存，完成前向计算与采样后回传 token，如此循环直到生成结束，最终由 API Server 返回响应。

前面几节讲的都是「怎么把显存用得更满、把请求排得更顺」，但这些策略最终都要落到具体的执行者身上——真正把模型权重加载进显存、把每一轮迭代的 kernel 跑起来的，是 vLLM 里的 GPU worker。理解它的职责，有助于把前面零散的概念串成一条完整的执行链路。

GPU worker 是什么

在 vLLM 的架构里，进程角色大致可以分成两类：

  • API Server / Engine Core：负责接收 HTTP 请求、做 tokenize、维护调度器与请求队列，决定「这一轮迭代要算哪些请求」；
  • GPU worker：负责「真正去算」。它持有模型权重、KV cache 的物理显存，接收 Engine Core 下发的执行计划（哪些请求、各自的 block 映射表、本轮要算多少 token），调用模型前向计算，再把新生成的 token 与采样结果回传。

一句话概括：Engine Core 负责「决定算什么」，GPU worker 负责「把它算出来」。调度器再聪明，也只是产出一份执行计划；没有 worker 去执行，计划就只是纸面上的数字。

一次迭代里 worker 做了什么

把前面「一次前向迭代」的概念落到 worker 上，它在一轮迭代中大致完成这几步：

  1. 接收执行计划：拿到本轮参与计算的请求列表、每条请求的输入 token（prefill 阶段是整段 prompt，decode 阶段是新生成的单个 token），以及逻辑块到物理块的映射表；
  2. 准备输入张量：按 PagedAttention 的要求，把 token 拼成批次张量，并把 block table、序列长度等元信息一并组织好；
  3. 执行前向计算：调用模型跑一遍所有层，注意力部分通过 PagedAttention kernel 按 block table 去读 KV cache，并把新算出的 K、V 写回对应的物理块；
  4. 采样并回传：对输出的 logits 做采样得到下一个 token，把结果连同更新后的 KV cache 状态返回给 Engine Core。

可以看到，前面讲的 PagedAttention、连续批处理、分块 prefill，最终都体现为 worker 这一侧的输入组织方式与 kernel 调用方式——调度策略决定「批次长什么样」，worker 决定「这个批次怎么算」。

单卡与多卡：worker 的组织方式

  • 单卡部署：一个 GPU worker 独占一张卡，模型权重与 KV cache 都放在这张卡的显存里，是最简单的形态；
  • 张量并行（TP）：模型一层被切分到多张卡上，每张卡一个 worker，它们在同一次迭代中协同完成一次前向计算，通过 all-reduce 等通信同步中间结果；
  • 流水并行（PP）：把不同层放到不同卡上，worker 之间按层顺序传递激活值。

多卡场景下，--tensor-parallel-size 与 --pipeline-parallel-size 决定的就是 worker 的数量与切分方式。这也解释了一个常见现象：显存不够时，加卡往往比调参更直接——因为加卡本质上是在增加 worker、分摊权重与 KV cache 的占用。

与前面几节的关系

前面讲的概念 在 GPU worker 上的体现
KV cache / PagedAttention worker 持有物理 block，按 block table 读写 KV cache
连续批处理 worker 每轮接收一份新的执行计划，批次成员可以变化
分块 prefill worker 每轮只对长 prompt 的一部分做 prefill，剩余留给 decode
抢占（Swap / Recompute） worker 负责把 KV block 拷出到 CPU，或丢弃后重新 prefill
量化 worker 加载的是低精度权重，前向计算按对应 kernel 执行

实践中的关注点

  • worker 数量与显存匹配：TP/PP 的切分要与卡数、单卡显存一起规划，切得太细通信开销会吃掉收益；
  • 启动日志里的 worker 信息：vLLM 启动时会打印每个 worker 的 device、显存占用与 KV cache block 数量，是排查「为什么并发上不去」的第一手线索；
  • 故障定位：OOM、kernel 报错、NCCL 通信超时通常都发生在 worker 侧，看到这类错误时应优先检查单卡显存与卡间通信，而不是调度参数。

一句话概括：GPU worker 是 vLLM 里「真正干活的那一层」，调度器给出计划、worker 负责执行；把 worker 的职责想清楚，前面关于 KV cache、批处理与量化的讨论就能串成一条从请求到算力的完整链路。

总结

  • vLLM 的定位：它站在大模型与硬件之间，不改变模型本身，而是通过更聪明的显存管理与请求调度，把同一张 GPU 的算力与显存榨得更充分，对外只需一条 vllm serve 就能提供 OpenAI 兼容服务。
  • KV cache：注意力的 K、V 只由对应位置的 token 决定，算过就不会变；把它们缓存下来复用，就能把每步重复的平方级计算降为一次，代价是缓存本身成为推理服务真正的显存瓶颈。
  • PagedAttention：借鉴操作系统分页思想，把 KV cache 切成固定大小的 block，用「逻辑块 → 物理块」映射表按需分配、灵活复用，让显存从「整块预留」变成「按页调度」，同时为 prefix caching 打下基础。
  • 连续批处理与调度器：调度粒度从「一整批请求的生命周期」细化到「一次前向迭代」，每轮迭代之间重新组批，请求结束即释放 KV block、新请求随时插入；显存不足时再通过换出或重算完成抢占。
  • 量化：用更低精度表示权重与激活，在显存与精度之间做交换；权重量化与 KV cache 量化是两件独立的事，可以叠加使用，但都需要用业务数据回归验证效果。
  • GPU worker：它是真正干活的那一层，持有模型权重与 KV cache 物理显存，按 Engine Core 下发的执行计划完成前向计算与采样——调度策略决定「批次长什么样」，worker 决定「这个批次怎么算」。

一次完整的输入输出过程

前面几节分别讲了 KV cache、PagedAttention、连续批处理、量化和 GPU worker，但它们并不是彼此独立的模块，而是同一条推理链路上的不同环节。这一节把整条链路完整走一遍：一条请求从进入 vLLM 到拿到完整回答，中间每一步分别由谁负责、用到了前面哪个机制、又消耗了哪部分显存。

阶段 0：启动时把显存切成两半

在服务对外提供接口之前，vLLM 先做一次「资源准备」，这一步决定了后面所有请求能借到多少空间：

  1. 加载模型权重：GPU worker 把模型参数读进显存。如果用的是 AWQ / GPTQ 量化模型，读进来的就是 4 bit 低精度权重，7B 模型从约 14 GB 降到约 4 GB——这是量化最直接的收益。
  2. 划分显存池：vLLM 按 --gpu-memory-utilization（默认 0.9）算出这张卡可用的显存总量，扣掉权重、激活、通信缓冲等开销，把剩余部分一次性预留成 KV cache 显存池，再按 --block-size（默认 16）切成固定大小的物理 block。启动日志里的 # GPU blocks: xxx 就是池子的容量。
  3. 建立前缀缓存表（可选）：若开启 --enable-prefix-caching，vLLM 会额外维护一张「前缀 hash → 物理 block」的索引表，供后续请求复用相同前缀的 KV block。

此后池子大小不再变化，所有请求都只是从池子里「借」block。可以记成一句话：权重是固定占用，KV cache 池是弹性占用，两者此消彼长——这也是为什么量化省下来的显存，最终会变成更大的并发能力。

阶段 1：请求进入 Engine Core

客户端通过 POST /v1/chat/completions 发起请求，API Server 接收后解析请求体，把 messages 按对话模板拼成一段 prompt 并 tokenize 成 token 序列，然后封装成序列对象交给 Engine Core。

Engine Core 是「大脑」，它不碰 GPU 计算，只负责决策：维护等待队列（waiting）与运行队列（running），并在每一轮迭代前决定「这一轮算哪些请求、各分配多少 block」。真正的计算全部由 GPU worker 执行——Engine Core 决定算什么，GPU worker 负责把它算出来。

阶段 2：调度器组批（连续批处理在这里发生）

调度器在每一轮迭代之间做三件事：

  1. 挑请求：按 FCFS 等策略从等待队列取请求，判断所需 KV block 能否从显存池中分配；
  2. 分块：为被选中的请求分配物理 block，建立「逻辑块 → 物理块」映射表；显存不够时触发抢占（Swap 换出到 CPU，或 Recompute 丢弃后重算）；
  3. 组批：把本轮要算的请求组成一个 batch，连同 block table、本轮 token 数一起下发给 GPU worker。

这里正是连续批处理的体现：批次不是一次性锁定到请求结束，而是每轮迭代都可以换人。某条请求这一轮生成了 EOS，下一轮它就不在批次里，它腾出的 block 立刻归还显存池给新请求用；新请求到达后，下一轮就能被塞进来一起算。所以 GPU 的每个迭代都尽可能被填满，长请求不会拖住短请求。

阶段 3：prefill——建立 KV cache

被选中的新请求进入 prefill：GPU worker 把整段 prompt 一次性送进模型，跑一遍所有层，算出所有 token 的 K、V，并按 block table 写入显存池中分配到的物理块，同时得到第一个输出 token。

这一步有两个细节值得注意：

  • KV cache 在这里诞生。注意力的 K、V 只由对应位置的 token 决定，算过就不会变，所以存下来后续直接复用，把每步重复的平方级计算降为一次。注意这是同一条请求内部的复用：这条请求在 decode 阶段每生成一个新 token，都要回头读自己前面所有 token 的 K、V，靠的就是这份缓存。
  • prefix caching 在这里生效。它解决的是跨请求的复用问题：如果开启前缀缓存，worker 会先按前缀 hash 查表，看别的请求是否已经算过一段完全相同的前缀；命中则直接复用那些物理块，只对未命中的后缀做 prefill。多个请求共享同一段系统提示词时，第二次请求的 prefill 计算量会大幅减少，首 token 延迟明显下降。

两者的区别可以整理成一张表：

对比项 KV cache prefix caching
复用范围 同一条请求内部 不同请求之间
复用内容 自己已生成 token 的 K、V 其他请求算过的、完全相同的前缀 block
生效阶段 prefill 建立，decode 全程使用 只在 prefill 阶段查表命中
是否默认开启 是，KV cache 是推理的基本机制 否，需 --enable-prefix-caching
命中条件 天然命中，就是自己的历史 前缀必须逐 token 完全一致

换句话说：KV cache 是「自己记住自己算过的东西」，prefix caching 是「借用别人算过的、且和自己开头一模一样的那部分」。前者是推理的必备机制，后者是在 KV cache 之上、借助 PagedAttention 的物理块共享能力做的一层跨请求优化。

如果 prompt 很长，且开启了 --enable-chunked-prefill，这次 prefill 会被按 --max-num-batched-tokens 的预算拆成多轮，每轮只算一块，剩余预算留给正在 decode 的请求，避免长 prompt 把同批次的 decode 请求卡住。

阶段 4：decode 循环——PagedAttention 的主场

prefill 结束后请求转入 decode：此后每轮迭代只输入上一个新生成的 token，worker 通过 PagedAttention 按 block table 读取历史 KV cache、追加新 token 的 K、V，再采样出下一个 token。

PagedAttention 的价值在这里体现得最充分：

  • 历史 KV cache 分散在不连续的物理块里，靠 block table 拼成逻辑上连续的序列，无需为每条请求预留连续显存，内部碎片几乎消除；
  • 请求长度增长时按需再借新 block，用完即还，不同请求的物理块可以灵活复用；
  • 相同前缀的请求共享物理块，这正是 prefix caching 的底层基础。

每一轮 decode 结束后，控制权回到 Engine Core：调度器重新组批，检查是否有请求结束、是否有新请求到达、显存池是否还够。prefill 只发生一次，decode 会重复很多次，而每一轮迭代都是一次完整的「调度 → 下发 → 前向计算 → 采样 → 回传」循环。

阶段 5：结束与返回

当生成到 EOS 或达到 max_tokens 时，该请求被移出批次，它占用的 KV block 归还到显存池供后续请求复用；API Server 把累积的 token 做 detokenize，按流式（SSE）或一次性响应的方式返回给客户端。

各环节职责一览

环节 由谁负责 用到的机制 显存影响
加载权重 GPU worker 量化（AWQ / GPTQ / FP8） 固定占用，量化后大幅下降
划分显存池 Engine Core + worker --gpu-memory-utilization、--block-size 决定 KV cache 池容量
接收与 tokenize API Server 对话模板 不占 GPU 显存
组批与分配 block Engine Core 调度器 连续批处理、抢占 从池中借出 block
prefill GPU worker KV cache 建立、prefix caching、分块 prefill 写入新 block
decode GPU worker PagedAttention 读写、连续批处理 逐轮追加 block
结束回收 调度器 + worker 释放 block block 归还池中

一句话串起来：权重在启动时占住显存，显存池在启动时划好；请求进来后由 Engine Core 每轮组批，GPU worker 在 prefill 时建立 KV cache（prefix caching 可复用前缀），在 decode 时靠 PagedAttention 按页读写缓存；连续批处理让每轮迭代都能换人，量化则从源头把权重压小、给 KV cache 腾出更多空间。

flowchart TD

  B --> C["Engine Core<br/>请求入等待队列 waiting"]
  C --> D{"调度器本轮组批<br/>显存池中 KV block 是否够分配"}

  G -- "未命中" --> I["prefill：整段 prompt 前向计算<br/>写入 KV cache，得到首个 token"]
