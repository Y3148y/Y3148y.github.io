Agent每日一题01：大模型持续学习：灾难性遗忘、EWC 与 LoRA 参数隔离

发表于2026-10-27|更新于2026-10-27|面试问答
|浏览量:

1. 面试现场：一个看似简单的问题

面试官问你：
一个大模型微调，先微调了法律知识，又微调了医疗知识，结果法律能力全丢了，加数据混合能解决吗？

你回答：不能。旧数据拿不到，比例也调不好。

追问：那为什么有的方案能持续学习新任务，还不忘记旧的？

又答不上来了吧。

这里涉及的就是持续学习中的
灾难性遗忘、弹性权重固化（EWC）和参数隔离机制。
考的是模型知识保持和参数更新边界的工程理解。

2. 微调到底调了啥：从权重说起

先把最基础的问题说清楚：微调调的就是模型的权重（参数），而且是神经网络里那一堆权重矩阵和偏置。

一个神经网络可以看成一张巨大的参数表。以 Transformer 为例，每一层里都有：

  • 注意力层的投影矩阵：W_q、W_k、W_v、W_o，负责把输入映射成 query/key/value 并做输出投影；
  • 前馈网络（FFN）的两层矩阵：先升维再降维，参数量通常占整层的大头；
  • LayerNorm 的缩放和偏置：γ、β，数量少但影响数值稳定性；
  • 词嵌入矩阵和输出头：词表有多大，这一块就有多宽。

这些矩阵里的每一个数字，都是训练时通过反向传播一点点更新出来的。所谓”微调”，就是拿一个已经预训练好的权重作为起点，用新任务的数据继续跑梯度下降，把这些数字往新任务更优的方向挪一挪。

所以”全参微调”调的是全部权重，”局部微调”调的是其中一部分权重——这正是后面 EWC 和 LoRA 的分歧所在：前者想办法约束哪些权重不能乱动，后者干脆只让一小部分权重参与训练。

2.1 权重里到底存了什么

一个常见的误解是”知识存在某一层”。实际上，预训练模型学到的知识是分散在大量权重里的分布式表示，没有哪个矩阵专门存”法律知识”、哪个矩阵专门存”医疗知识”。

这也解释了为什么灾难性遗忘难以避免：新任务的梯度更新不区分权重的重要性，只要某个权重对降低新任务损失有用，它就会被改，而它可能恰好也是旧任务依赖的。权重是共享的，知识就是耦合的。

2.2 训练数据到底是什么

训练数据是外部样本（文本、问答对、图片标签），不进模型结构；参数（权重）是模型内部那堆数字，是训练后沉淀下来的”学到的知识”。训练就是拿数据反复前向、算损失、反向传播，把梯度作用到参数上——数据是输入，参数是输出，数据用完可丢，参数会留下。

这也解释了旧数据丢了为什么麻烦——参数里只留下旧数据训练后的结果，原始样本没了就没法再算梯度、做回放，只能从参数层面保护，这正是 EWC 和 LoRA 要解决的问题。

至于”自己存一份旧数据”，真实工程里往往卡在几道坎上：数据不归你（合同常写明”仅用于本次训练、不得留存”）、隐私合规（医疗金融法律样本脱敏授权审计成本比训练还高）、流式一次性（线上日志训完即弃）、存了也未必能用（分布会变，全量回放可能比重训还贵）、跨团队跨版本（数据在别的部门或基座换了版本，对应关系已断）。

一句话：能存最好，存不了才是常态——方案要按”旧数据拿不到”这个最坏情况来设计。

3. 先搞清楚：持续学习到底在问什么

持续学习到底怎么判断哪些参数能改，哪些必须冻结，旧知识存在哪一层？

很多人的第一反应是：把新旧数据混在一起训练就行了。但真实情况要细得多。

  • 全参微调时，新任务的梯度会覆盖旧任务学到的权重，模型容量被新任务占满，旧任务的表现断崖式下跌。
  • 混旧数据时，旧数据可能已经拿不到了；比例调不好，还会两头不讨好。

所以在默认全参数微调、无参数保护的场景下，答案就是不能。

但面试时如果只答”不能”，其实只答对了一半。
更完整的回答是分情况：
默认全参微调下，新任务会覆盖旧任务的参数，旧知识发生灾难性遗忘，这条路走不通；可一旦引入弹性权重固化 + 参数隔离 + LoRA 适配器这套配置，答案就变成”可以”——EWC 负责保护对旧任务重要的参数，LoRA 则为每个任务提供独立的适配器，两者配合，新任务学得进、旧任务忘不掉。

4. 灾难性遗忘的成因

一个模型要学习新任务，本质上是调参数让新任务的损失下降。默认规则下，全参微调对所有参数一视同仁，新任务的梯度更新不区分哪些参数对旧任务重要。

旧任务的知识分散在大量参数里，新任务训练时这些参数被大幅修改，旧知识被覆盖，这就是常见的知识遗忘。

更麻烦的是，旧任务的训练数据因为隐私或者存储原因已经不可用，没法做数据回放（Replay）。数据回放这条路走不通，就只能从参数层面想办法。

4. 方案一：弹性权重固化（EWC）

持续学习提供了多个层面的方案，其中一个叫弹性权重微调，也就是 EWC（Elastic Weight Consolidation）。

EWC 的核心思路是 Fisher 信息：先估计每个参数对旧任务的重要性，重要性越高的参数，在学新任务时越要”拉住”它，不让它被大幅改动。

这样新任务仍然能学，但不会把旧任务的关键权重冲掉。代价是需要额外计算 Fisher 信息矩阵，并且要为每个旧任务保存一份重要性权重，任务一多，存储和计算开销都会上升。

5. 方案二：参数隔离 + 低秩适配（LoRA）

另一个思路是参数隔离，典型代表就是 LoRA（Low-Rank Adaptation）。

LoRA 的做法是：冻结预训练模型的大量权重矩阵，只引入低秩矩阵作为适配器参与训练。不同任务各自训练一套适配器，参数天然隔离，互不干扰。

5.1 多科室医疗问答系统

在多科室医疗问答系统里，先上线了神经内科模型，最后上线儿科。如果每次都用全参数微调，后面科室会覆盖前面科室。

用 LoRA 微调，每个科室一个适配器，推理时根据科室路由到对应的适配器，互不干扰。

几个工程上必须注意的点：

  • 主干只加载一份：所有科室共享同一个基座模型，显存占用约等于「一个基座 + N 份小适配器」，而不是 N 个完整模型；
  • set_adapter 是切换开关：它只改变前向时走哪套低秩分支，不会改动主干权重，所以科室之间天然零干扰；
  • 适配器要按科室命名并做版本管理：adapter_name 建议直接用业务标识，方便灰度、回滚和 A/B 对比；
  • 路由层要能兜底：科室识别不出来时，走通用适配器或直接回退到基座模型，别让请求直接报错；
  • 并发场景下别共享可变状态：多线程/多请求同时推理时，set_adapter 是全局状态，建议按适配器做模型实例池，或改用支持 per-request adapter 的推理框架（如 vLLM 的 multi-LoRA）。

5.2 其他典型场景

  • 推荐系统：用户喜好不断变化，不同阶段、不同人群可以挂不同适配器。
  • 企业知识库：新文档不断进来，按业务域拆分适配器，避免新知识冲掉旧知识。

6. 怎么判断一个持续学习方案好不好

面试里如果被追问”那你说说，怎么评价一个方案行不行”，别只背名词，直接给四条判断标准，一条一条对着看：

  • 旧任务关键参数有没有做保护：看方案是否显式估计了参数对旧任务的重要性（比如 Fisher 信息），并对关键参数施加约束。没有这层保护，新任务的梯度就会无差别地冲刷旧权重。
  • 参数隔离有没有做到任务间零干扰：看不同任务的更新是否落在互不重叠的参数子空间上。LoRA 冻结主干、每个任务一套低秩适配器，天然满足；如果多个任务共用同一份可训练参数，就谈不上隔离。
  • 适配器有没有做冲突消解：任务一多，适配器之间会出现语义重叠甚至相互打架。要看有没有路由策略、合并策略或者冲突检测机制，而不是简单堆一堆适配器了事。
  • 线上分布偏移有没有做监控和回滚：模型上线后数据分布会漂移，旧任务的表现可能悄悄退化。要有指标监控、灰度发布和快速回滚能力，否则离线指标再好看，线上也可能翻车。

6.1 适配器冲突消解具体怎么做

“冲突消解”听起来抽象，落到工程上其实是四层动作，从粗到细依次是：路由、合并、检测、隔离。

第一层：路由（Route）——先保证”该用谁就用谁”

冲突的根源往往是”用错了适配器”。所以第一件事是把路由做准：

  • 显式路由：请求里带业务标识（科室、业务域、租户 ID），直接映射到 adapter_name，最稳、最可控；
  • 隐式路由：请求里没有标识时，用一个轻量分类器（小模型或规则）判断意图，再选适配器；
  • 兜底路由：识别不出来就走通用适配器或直接回退基座模型，绝不让请求报错。

第二层：合并（Merge）——多个适配器都要用时怎么合

当一个请求同时涉及多个领域（比如”儿科用药对肝肾功能的影响”），需要同时激活多个适配器。常见做法：

  • 加权合并：把多个 LoRA 的 B@A 低秩增量按权重相加，W' = W + Σ w_i · B_i A_i，PEFT 里可用 add_weighted_adapter 实现；
  • 串行/交替：先走 A 适配器再走 B，适合有明确先后顺序的场景；
  • 任务算术（Task Arithmetic）：把适配器当成”任务向量”做加减，用于合并同类任务、抵消冲突方向。

第三层：检测（Detect）——怎么知道它们打架了

合并之前要先判断”能不能合”，否则越合越差。可用的检测手段：

  • 输出一致性检测：同一批探针问题分别用 A、B、A+B 推理，比较答案差异，差异过大说明冲突；
  • 参数相似度：计算两个适配器低秩矩阵的余弦相似度，方向越接近越容易合并；
  • 回归测试集：每个适配器维护一组”能力探针”（golden set），合并后跑一遍，看各自领域指标掉没掉。

第四层：隔离（Isolate）——实在合不了就分开

如果两个适配器冲突严重（比如法律和医疗对同一表述的倾向完全相反），最稳妥的做法是不合并：

  • 按请求维度拆实例，各自加载各自的适配器，物理隔离；
  • 用支持 per-request adapter 的推理框架（如 vLLM 的 multi-LoRA），一次前向只挂一个适配器；
  • 冲突无法调和时，宁可多训一个”融合适配器”，也不要在推理时硬拼。

一句话总结：冲突消解不是某一个算法，而是一套流程——先用路由保证选对，再用合并处理多领域，用检测判断能不能合，最后用隔离兜住合不了的情况。面试时能把这四层讲清楚，比只答”用路由”要扎实得多。

这四条其实对应了持续学习的两个核心问题：参数更新边界（前两条）和工程可控性（后两条）。能同时答上来的，才算真正理解了持续学习，而不只是记住了 EWC 和 LoRA 两个缩写。

7. 工程落地：为什么实际工作几乎不做全参微调

实际工作当中，全参数微调基本不会做，因为很大概率会遇到灾难性遗忘问题。这很恐怖，很有可能一个项目被拖了再拖，最后黄了。

所以都会选择局部微调，比如 LoRA 和 Adapter。

模型微调基本集中在这些场景：

  • 文本提取
  • 短文本生成
  • 报告格式
  • 语气基调

实际工作中，微调需要考虑成本和效率的天平。所以 LoRA 几乎就是工作中微调大模型的性价比之王。

可以理解为：在保留预训练模型大量权重矩阵的同时，引入低秩矩阵作为适配器，这样就能做到有效分离。

8. 面试回答

得看情况。默认全参微调、不做任何保护，那不能——旧数据拿不到，比例也调不好。

因为全参微调时梯度对所有参数一视同仁，不区分哪个对旧任务重要，新任务一训就把旧权重冲了，这就是灾难性遗忘。

但持续学习有两条路：EWC 用 Fisher 信息找出关键参数，加惩罚项拉住它；LoRA 干脆做隔离，冻结主干，每个任务一套适配器，推理时按任务路由，互不干扰。两个还能组合，EWC 保参数、LoRA 隔任务，就能学新的不忘旧的。

工程上基本不做全参微调，风险太大，都是局部微调，LoRA 性价比最高。

判断方案行不行，我就看四点：关键参数有没有保护、参数隔离是不是真零干扰、适配器有没有冲突消解、线上分布偏移有没有监控和回滚。

追问细节时，补一张对比表兜底：

方案 核心思想 优点 代价
数据混合 新旧数据一起训 实现简单 旧数据可能不可得，比例难调
EWC Fisher 信息约束关键参数 单模型承载多任务 需存重要性权重，开销随任务增长
LoRA / Adapter 参数隔离，低秩适配 互不干扰，成本低 需管理多套适配器与路由

一句话收尾：面试不是回答”能不能”，而是分情况——默认全参微调会让新任务覆盖旧参数、造成灾难性遗忘；而 EWC 保护关键参数、LoRA 为每个任务提供独立适配器，这套组合配置就能做到持续学习新任务而不忘旧的。判断一个方案好不好，就看四点：关键参数有没有保护、参数隔离有没有做到零干扰、适配器有没有冲突消解、线上分布偏移有没有监控和回滚。

1. 面试题还原面试官问：多轮对话如何处理？ 一个场景题：如果一个员工问「工作时长是多少？年假是多少？调休是多少？」，接着又问「这个怎么算？」——你的「这个」是怎么处理的？怎么让大模型知道「这个」指代什么？ 这道题表面在问「多轮对话」，实际在考三件事： 指代消解：能不能把「这个」还原成上一轮的具体实体（工作时长 / 年假 / 调休）。 状态管理：多轮信息存在哪、怎么更新、怎么不串味。 工程兜底：模型抽错了怎么办、缓存怎么复用、答不出来怎么降级。 一句话总结答题主线：状态管理 + 缓存复用 + 校验兜底。 2. 为什么多轮对话难：问题本质单轮 RAG 的链路是「问题 → 检索 → 生成」，问题本身是自包含的。多轮对话里，用户的问题往往是不完整的： 轮次 用户输入 是否自包含 缺失信息 第 1 轮 工作时长是多少？ 是 无 第 2 轮 年假是多少？ 是 无 第 3 轮 调休是多少？ 是 无 第 4 轮 这个怎么算？ 否 「这个」指代谁 如果直接把「这个怎么算？」丢给检索，向量库里全是「这个」「怎么算」这种无信息量的词，召回必然...
