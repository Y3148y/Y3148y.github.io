给 Hexo 博客加一个本地写作后台

发表于2026-10-18|更新于2026-10-20|技术学习
|浏览量:

前言

写博客这件事，Hexo 的门槛其实不在「写」，而在「发」。

文章是 Markdown，纯文本记事本就能写。但每次写完想上线，得打开终端、敲 hexo clean、等构建、再敲 hexo deploy。构建要十几秒，推送可能因为网络抖动失败，失败了还得看着 fatal: unable to access ... 猜原因。写作是连续的，发布是离散的，中间这段割裂感才是真正的成本。

所以我给自己的博客加了一个本地后台：浏览器里写，预览，保存，点一下按钮直接上线。

这篇文章记录这次实现的全过程——架构怎么定的、代码怎么组织的，以及踩了哪些坑。后者占的篇幅可能比前者还多，因为那几个坑里有几个挺典型的。

整体架构

先说清楚边界。这个后台不是 CMS，不是网站的一部分，它是一个只在本机运行的 Node 进程，通过 HTTP 提供一个网页界面，最终仍然产出标准的 Markdown 文件交给 Hexo：

有三条约束贯穿整个设计：

1. 零新增运行时依赖。

写完之后对比 package.json，17 个依赖一个没动，只多了一条 npm script：

这一点不是洁癖。个人博客的 node_modules 越大，npm install 越慢、CI 缓存越容易失效、依赖冲突的排查面越宽。而一个管理界面真的需要什么？HTTP 服务 Node 内置就有，密码哈希 node:crypto 有，图片上传 FileReader 前端就能转 base64。真正需要的 js-yaml 是 Hexo 自己的传递依赖，直接 require 就行。

2. 只监听本机。

默认 127.0.0.1，不对局域网暴露。个人写作工具的威胁模型很简单：别人碰不到你的机器就行。

3. 与现有构建链路同源。

后台不重新实现「构建站点」，它调用的还是 hexo clean / generate / deploy。这样保证了「后台里看到的」和「线上呈现的」不会出现两套逻辑。

代码规模：

模块 行数 职责
public/app.js 784 前端全部逻辑（无框架、无构建）
lib/deploy.js 321 构建、部署、凭据预检、代理降级
public/style.css 294 样式
server.js 247 HTTP 路由分发
lib/frontmatter.js 163 YAML 解析与序列化
lib/posts.js 143 文章 CRUD
lib/auth.js 126 鉴权与会话
其余 9 个 ~660 工具、图片、快照、定时器等
合计 2844

为什么不用现成方案

社区确实有个 hexo-admin，看起来正好干这件事。但我去看了它的依赖：

hexo-fs@0.1、hexo-util@0.1 是 Hexo 3 时代的版本号，而本项目用的是 hexo-fs@5 / hexo-util@4。主版本号都不在同一个时代，装上去大概率跑不起来。它的最后更新停在 2022 年。

「装个现成的」省下的时间，远少于「把一个腐朽的依赖树从零剥离」花的时间。于是决定自己写。

第一步：frontmatter 的序列化

这是整个后台里最容易出错、也最有价值的一块。

为什么不用 yaml.dump

最直接的想法是 yaml.dump(data)。但它不可控：会把字符串形式的日期加引号（正是要避免的）、键顺序随对象插入顺序变化、null 和空数组的表示方式也不符合我想要的格式。

所以写了一个专用的序列化器，163 行，规则完全自己定：

每一行都对应一类真实会咬人的情况：

  • 标题以 # 开头 → 会被当成注释
  • 标签写成 true / 123 → 会被反序列化成布尔或数字
  • 某个封面路径恰好写成 2026-01-01 → 会被反序列化成 Date

最后一条尤其隐蔽：它本来是个合法的图片路径，却因为长得像日期而类型漂移。所以规则是宁可多加引号，绝不产生类型歧义。

往返无损怎么验证

「保存后再打开内容没变」听起来是废话，但在这个场景下它是个真问题：格式归一（BOM、尾部空行、引号）会造成字节不同，而语义必须完全一致。

我的验证方式是逐篇跑三个判据：

  1. frontmatter 解析后深度相等（忽略键顺序）
  2. 正文相等（归一化 BOM 与尾部空白后）
  3. 幂等：再存一次，输出必须逐字节相同

第三条最关键。如果序列化不幂等，意味着每点一次保存文件就变一次，git 历史会被垃圾提交淹没。

最初有 5 篇文章没能通过第三项，查下来是围栏后空行和文末换行的处理不一致——有的文章围栏后有空行、有的没有。统一成「围栏后恒定一个空行、文末恒定一个换行」后，14 篇文章全部通过。

第二步：HTTP 服务与鉴权

不用 Express

一个只有 19 条路由、只跑在本机的工具，引 Express 意味着引入 60 多个传递依赖。node:http 写一个路由分发器并不复杂，而且我对路由表的掌控度更高。

口令与会话

口令用 scrypt 哈希存储，比 PBKDF2 更抗 GPU 破解：

会话用 HMAC 签名的自包含 token，不存服务端会话表。校验时必须用 timingSafeEqual 而不是 ===，否则存在时序侧信道：

CSRF 防护用了两层：Cookie 带 SameSite=Strict，同时要求所有变更请求带一个自定义头 X-Admin-Request: 1。跨站表单发不出自定义头，攻击面就被掐断了。

第四步：历史版本与定时发布

历史版本是在每次保存和删除前把文件的完整原文存一份快照。这里存原文而不是只存正文或字段快照，是为了在 frontmatter 也被改错时依然能完整回退。

回滚时先给当前版本做一次快照，这样「回滚」本身也能被撤销。

定时发布是一个 30 秒轮询的定时器，检查到点的任务就触发一次完整构建。它有两个必须注意的点：

  • 到点后先标记完成再执行，避免部署失败时无限重试
  • 启动时清理指向已删除文章的僵尸任务

CI 自动部署：四个坑

后台的第三个模式依赖 GitHub Actions。这部分我踩了四个连续的坑，值得完整记下来。

三个仓库的分工

先澄清一个常见误解。CI 工作流放在私密的内容仓库里，不是因为搞错了，而是因为产物仓库里根本没有源码：

仓库 可见性 内容
Y3148y/my-blog 私密 文章、配置、后台代码、工作流定义
Y3148y/hexo-theme-butterfly 公开 主题定制（CI 从这里拉）
Y3148y/Y3148y.github.io 公开 只有产物：index.html、css/、js/

github.io 那个仓库的 17 个顶层条目全是构建产物，连 package.json 都没有。拿产物构建产物是不可能的，所以工作流只能待在有源码的地方。

主题定制为什么必须 Fork

站点的油画画廊、音乐播放器、访客欢迎卡、L2D 挂钟，全在 themes/butterfly 里。而该目录被 .gitignore 忽略，定制只存在于本机。Actions 跑在 GitHub 的云端机器上，看不见我的硬盘。

坑四：Fine-grained PAT 的授权范围

注意这里的关键信息是身份被正确解析成了 Y3148y——说明令牌有效、认证通过，问题在授权范围。

定位方式是比较响应头：

经典 PAT 的 X-OAuth-Scopes 一定有值。空值 + 出现 expiration 头，说明这是 Fine-grained PAT。

两者的授权模型完全不同：

  • 经典 PAT：勾一个 repo 就覆盖名下所有仓库
  • Fine-grained PAT：必须逐个仓库授权，默认只勾当前所在的仓库

所以必须把 Y3148y.github.io 也加进授权列表，Contents 权限设为 Read and write。

一个附带的安全问题

排查过程中，我把一个完整的 PAT 明文贴进了对话里。这属于明文密钥泄露，标准处置是立刻吊销重建。

顺带说一句：排查令牌权限时，更安全的做法是让 CI 自己打印脱敏结果，而不是把令牌拿到本地 curl。我当时图省事走了捷径。

三次让用户当我的调试工具

CI 调试那一轮我连续失败四次，每次都是：写完 → 推送 → 让用户去 Actions 页面截图发给我 → 我猜。中间我甚至起过「本地复现 CI」的念头，然后被打断，就再没回来做。

根因只有一个：工作流脚本我一次都没在本地执行过就推上去了。

补上本地验证之后，很多问题一次就确认了：

  • 构建：完整跑一遍，148 个文件，13 秒
  • 推送：构造一个非空的本地远端复现 non-fast-forward，再验证 --force 能修复
  • 诊断脚本：用桩 curl 在 bash -e 下跑三种令牌场景，校验退出码

还有一次是验证降级重试：我在沙箱仓库里把本地 http.proxy 指向死端口 127.0.0.1:1，使直连必然失败，然后验证带 -c 覆盖参数的代理重试能成功——确定性可判定，不依赖网络抖动碰运气。

另一个同类问题：detectProxy() 的第一版我在 net.connect 的回调里写了 return，那毫无意义，函数会立刻返回第一个候选，等于根本没检测。不实际跑一次根本发现不了。

忘了后台口令 admin/data/config.json 里是 scrypt 哈希，无法反解。删掉该文件重启会重新生成并打印新口令
后台能开但文章存不进去 检查 source/_posts/ 目录权限；.gitignore 里的 /admin/data/ 是凭据目录，不要手动删它以外的 admin 文件
预览里 {% art_gallery %} 不显示画廊 预期行为。浏览器端没有 Hexo 渲染管线，这类标签预览时显示为说明卡片，线上由 scripts/art-gallery.js 渲染
图片上传提示格式不支持 只接受 JPG/PNG/GIF/WebP/AVIF/BMP/ICO。SVG 被拒——它能携带脚本，且 Hexo 会原样发布到公网
改了标题但线上 URL 没变 permalink 的 :title 取自文件名。需要在文章属性里勾「改标题时同步重命名文件」再保存
CI 每次推送都发失败邮件 检查仓库 Secrets 是否配齐；工作流会在第一步预检并明确指出缺哪个变量
定时发布没触发 定时器在后台进程里，关掉终端就不会执行
文章封面变成 404 错误图 error_img.post_page 的兜底生效了，说明 frontmatter 里的 cover 路径指向的文件不存在

总结与后续

这个后台的核心并不复杂：一个只在本机跑的 Node 进程，把 Markdown 文件的编辑工作从「开终端」搬到「开浏览器」。技术上最花心思的反而是序列化那块——因为要保证「在后台里保存一篇文章」和「用记事本改这篇文章」产生的文件在语义上完全等价。

几条经验留给自己：

  1. 序列化必须幂等。 不幂等的保存会持续污染 git 历史。
  2. 下「未被引用」的结论之前，先确认搜索范围是完整的。 我因为漏搜 frontmatter 而删掉了自己的文章封面。
  3. 脚本要先在本地跑通再推上去。 反复让别人当调试工具，本质上是把本该自己做的验证外包了。
  4. 失败日志要能自解释。 那些「退出码 1 然后什么都没有」的失败，是最消耗时间也最让人恼火的。CI 里加预检和分类提示，价值远超它的实现成本。

后续可以做的：编辑器支持分屏对照 diff、给 {% mermaid %} 做所见即所得的图形编辑、定时发布与 GitHub Actions 打通（推送后由云端在到点时构建，而不是依赖本机进程常驻）。
