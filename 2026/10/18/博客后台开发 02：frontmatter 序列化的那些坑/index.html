序列化：为什么它是整个后台最难的一块

上一篇讲了后台的整体结构和各个模块怎么实现。其中有一块我单独拎出来讲，因为它和我的博客无关，任何写 Hexo 工具的人都可能踩到，而且踩到的表现极其隐蔽：文件看起来完全正常，文章也能正常显示，但发布时间悄悄变了。

这一篇讲 frontmatter 的解析与序列化：一个后台要在「表单里的字段」和「磁盘上的 YAML 文本」之间来回转换，这件事听起来是十行代码的工作，实际上是整个项目里最容易写错的地方。

坑一：YAML 时间戳的 UTC 陷阱

现象

YAML 规范里，2026-10-18 14:30:00 这种格式是一个 timestamp 类型。js-yaml 解析它时不会给你一个字符串，而是给你一个 JavaScript Date 对象：

注意那个 Z。YAML 的 timestamp 没有时区标注时，按 UTC 解释。 而文件里写的 14:30，我写的时候心里想的是东八区的 14:30。

这就是第一个坑的入口：文件里没有任何信息能区分「UTC 的 14:30」和「东八区的 14:30」。 你以为它带时区，其实不带。

为什么它会静默改变发布时间

现在看保存路径。如果我在序列化时把日期写成带引号的形式：

再解析回来，得到的就是字符串 "2026-10-18 14:30:00"，不再是 Date。

而 Hexo 对这两种类型的时间处理是不同的——字符串走本地时区解析，Date 对象直接用。于是同一份文件，一次保存后文章的发布时间就可能被挪动 8 小时，进而改变它在本月归档里的排序位置，甚至从「今天」变成「昨天」。

这类 bug 极难发现，因为：

  • 文件内容「看起来」没变，只是多了引号
  • 文章能正常渲染
  • 只有日期跨了边界时，排序才错乱

出口必须统一

所以规则很明确：不管传进来的是 Date 还是字符串，出口永远统一成不带引号的 UTC 时间戳。

坑二：yaml.dump 不可控

最直接的想法是 yaml.dump(data)。它当然能输出合法 YAML，但有四个我无法接受的地方：

  1. 会把字符串形式的日期加引号（正是坑一要避免的）
  2. 键顺序随对象插入顺序变化——表单字段顺序和文件里原有顺序不一致时，每次保存都会重排整个 frontmatter
  3. null 和空数组的表示方式不符合常见写法（null / [] 混杂）
  4. 长字符串会被折行（lineWidth 默认 80）

条件 裸着写会变成 真实场景
以 # 开头 注释 标题写成 # 标题
以 - 开头 序列 标签写成 -教程
以 : 开头 映射 副标题写成 : 备注
等于 true/yes/no 布尔 标签就叫 no
长得像数字 数字 分类叫 2026

所以整个函数的策略是：宁可多加引号，绝不产生类型歧义。 多余的引号不会破坏任何东西，错误的类型会。

坑五：键顺序与未知字段

序列化时有个容易忽略的问题：文件里可能有你的表单里根本没有的字段。

我的博客里有篇文章用了 top_img，还有几篇用了 description。如果序列化时只输出表单认识的字段，这些值就在第一次保存时被静默删掉了——而且不会有任何报错，只是文章的行为变了（比如顶部图片没了）。

幂等：比「内容没变」更严格的要求

写完解析和序列化，我给自己定的验收标准不是「保存后再打开，内容没变」——那太宽松了。格式归一（BOM、尾部空行、引号）会造成字节不同，而语义必须完全一致。所以是三个判据：

  1. frontmatter 解析后深度相等（忽略键顺序）
  2. 正文相等（归一化 BOM 与尾部空白后）
  3. 幂等：再存一次，输出必须逐字节相同

第三条最关键。如果序列化不幂等，意味着每点一次保存文件就变一次，git 历史会被垃圾提交淹没——一年下来你的 git log 里全是「update via admin」，完全无法审查。

我最初的实现有 5 篇文章没能通过第三项。查下来是围栏后空行和文末换行的处理不一致——有的文章围栏后有空行、有的没有，而我的归一逻辑对这两种情况的处理结果不一致。

最终的输出格式固定成这一种：

四个「恒定」：围栏后恒定一个空行、正文结尾空白恒定被剥掉、文末恒定一个换行、换行符恒定是 \n（不是 \r\n）。最后一条在 Windows 上尤其重要——不显式归一，Windows 上保存的文件会比 Linux 上多出回车符，导致跨平台协作时反复产生 diff。

「恒定」这个词是幂等的本质。 不是「尽量保持原样」，而是「不管输入长什么样，输出都一样」。这两个目标在第一次保存时没有区别，到第十次就天差地别。

小结

  1. YAML 未加引号的时间戳按 UTC 解释，读写都要用 UTC 分量，别用 new Date(string)。
  2. 不要用 yaml.dump 做正文 frontmatter，它会重排键、加引号、折行。
  3. 字符串的「裸着安全」是一张可枚举的清单，抄走那十行 isPlainSafe 就能覆盖绝大部分。
  4. 用「往返类型检查」把防御变成可验证的，而不是靠人肉想「还有没有漏的」。
  5. 解析要逐行找围栏，正文里的 --- 是合法内容。
  6. 保留未知字段，否则表单不认识的字段会在第一次保存时静默消失。
  7. 幂等是硬要求，格式归一的四条「恒定」是实现它的前提。
