博客后台开发 01：整体架构与核心实现

发表于2026-10-18|更新于2026-10-20|技术学习
|浏览量:

这个系列在讲什么

给自己的 Hexo 博客加一个只在本机运行的后台，把「写文章」从开终端变成开浏览器。这个系列共三篇：

篇 主题 适合谁
01（本文） 为什么这么做、每个模块怎么实现 想自己动手搭一个后台的人
02 frontmatter 序列化 任何要写 Hexo 工具的人
03 部署与 CI 用 GitHub Actions 发静态站的人

01 讲整体取舍和实现细节。02 和 03 各自可以独立阅读。

先说清楚这个后台不是什么：它不是 CMS，不是网站的一部分，也不是要替代 Hexo。它只是一个跑在本机的 Node 进程，通过 HTTP 提供一个网页界面，最终仍然产出标准的 Markdown 文件交给 Hexo。这一点决定了后面所有的设计。

为什么不用现成的 hexo-admin

社区有个 hexo-admin，名字看起来正好干这件事。看它的依赖：

hexo-fs@0.1、hexo-util@0.1 是 Hexo 3 时代的版本号。我这个项目用的是 hexo-fs@5 / hexo-util@4，主版本号都不在同一个时代，装上去大概率跑不起来。它的最后更新停在 2022 年。

结论不是「社区方案都不好」，而是依赖树和宿主框架不同代，剥离成本高于重写成本。判断一个现成方案能不能用，看它的依赖主版本号和你的宿主是否处在同一个时代，比看 README 有没有写你的功能更有用。

三条设计约束

零新增运行时依赖

写完对比 package.json，17 个依赖一个没动，只多了一条 npm script：

这不是洁癖。个人博客的 node_modules 越大，npm install 越慢，CI 缓存越容易失效，依赖冲突的排查面越宽。而一个管理界面真的需要什么？

  • HTTP 服务 —— node:http 内置
  • 密码哈希 —— node:crypto 内置
  • 图片转 base64 —— 前端 FileReader 就有
  • YAML —— 真正需要的 js-yaml 是 Hexo 自己的传递依赖，require 进来即可

唯一的「新增依赖」是前端的 marked.min.js，我直接下载到 admin/public/vendor/ 里，连 npm 依赖都不算。

只监听本机

默认 127.0.0.1，不对局域网暴露。个人写作工具的威胁模型很简单：别人碰不到你的机器就行。为这个工具引入 HTTPS、OAuth、多用户体系，是解决了一个不存在的问题。

与现有构建链路同源

后台不重新实现「构建站点」，它调用的还是 hexo clean / generate / deploy。这样保证「后台里看到的」和「线上呈现的」不会出现两套逻辑。很多自建工具的坑就在于自己写了一套简化的构建，最后和真实构建产物不一致。

整体结构

注意最后那行：Markdown 文件是唯一的事实来源。后台没有数据库，所有状态都能从磁盘上的文件还原。这带来一个实际好处：后台挂了、数据目录丢了，文章一篇都不会少，重新 git clone 就回来了。

代码规模：

lib/deploy.js 321 构建、部署、凭据预检、代理降级
public/style.css 294 样式

lib/frontmatter.js 163 YAML 解析与序列化
lib/posts.js 143 文章 CRUD

合计 约 2800

会话与时序安全

会话用 HMAC 签名的自包含 token，不存服务端会话表：

两处细节值得单独说：

用 timingSafeEqual 而不是 ===。 字符串比较会在第一个不同的字节处提前返回，攻击者可以通过测量响应时间逐字节猜出正确的签名。只跑本机的工具其实用不上这个防护，但它是 crypto 内置的，写上零成本。

长度检查必须在前面。 timingSafeEqual 要求两个 buffer 等长，否则直接抛异常。如果不先判断长度，一个畸形的 Cookie 会让整个请求 500，而不是安静地判定为「未登录」。

历史版本与定时发布

快照存原文

每次保存和删除前，把文件的完整原文存一份快照：

存原文而不是只存正文或字段快照，是为了在 frontmatter 也被改错时依然能完整回退。存字段的话，一个写坏的日期字段就没法还原了。

回滚时先给当前版本做一次快照，这样「回滚」本身也能被撤销。默认每篇保留最近 20 版，超出的按时间裁掉。

定时器的两个细节

定时发布是一个 30 秒轮询的定时器，检查到点的任务就触发一次完整构建：

两个必须注意的点：

  • 到点后先标记完成再执行，避免部署失败时无限重试。如果你每次失败都重置「已完成」标记，一个网络问题就会变成每 30 秒重试一次的死循环。
  • 启动时清理指向已删除文章的僵尸任务（dropMissing）。文章在等待期间被删了，定时器还盯着一个已经不存在的 slug，任务会永远处于「待执行」状态。

还有个现实限制值得写在这里：定时发布依赖后台进程常驻。关掉终端，定时器就没了。我没有把它做成系统服务，因为那就要处理开机自启、日志轮转、进程守护——为一个每天可能用一次的功能引入这些，不划算。03 会讲怎么用云端定时任务替代它。

注意这里根本没有 SVG——不是「不支持」，是故意拒绝：

SVG 能携带 <script>，上传后就是一个放在自己域名下的任意脚本执行入口。即使它只跑在本机后台、只你自己看，Hexo 会把它原样发布到公网这件事，就已经让它变成一个必须拒绝的输入。

文件名用内容哈希，同名同内容自动复用：

ensureWithin 负责把最终路径限制在上传目录内，防止 ../ 穿越。这一点在任何接受用户提供的文件名的接口上都必须有，我把它放在了工具函数里，让所有调用点都自动受保护，而不是指望每个调用点记得写。

资源审计：别急着下「未引用」的结论

这个后台用 /img/... 引用站点里的图片，写文章时也用它做路径补全。有一阵子 source/img/ 下堆了不少文件，我做了个清理脚本，按「是否被引用」把图片分成在用和死文件两类，删掉了后者。

判断「是否被引用」时，搜索范围本身是错的。

我穷尽搜索了主题的 pug 模板、JS 脚本、stylus 和两个 yml 配置，确认某个图片零命中。但图片引用还可以出现在文章 frontmatter 里：

而 source/_posts/*.md 根本没在搜索范围内。这两个文件一失效，主题就按 error_img.post_page 回落到 /img/404.jpg——线上所有文章封面变成 404 错误图，而我在本地什么都没察觉，因为本地缓存还留着旧图。

事后重写的审计脚本覆盖了所有可能的引用点：主题模板、脚本、配置、全部 Markdown 的 frontmatter、_data 目录。扫描 226 个文本文件后才敢下结论。

这条教训的泛化版本是：在下「未被引用」这种结论之前，先问一句「有没有我搜不到的地方」。 这个判断很难自动化，因为它依赖「你知道有哪些地方能引用它」。至少要按引用类型枚举一遍：代码里的路径、配置里的值、内容文件里的 frontmatter、数据库里的记录。

本篇要点

  1. 判断现成方案能不能用，看依赖主版本号和宿主是否同代，比看功能列表有用。
  2. Markdown 文件作为唯一事实来源，后台不带数据库，挂了也不丢文章。
  3. 持久化的状态一定要有白名单校验，否则脏数据会把用户困死。
  4. 工具栏按钮分「包裹」和「前缀」两类，当成一件事做必然出 bug。
  5. 上传接口按魔数校验、默认拒绝 SVG，任何会原样发布到公网的输入都要按不可信处理。
  6. 下「未被引用」的结论前，先确认搜索范围完整。
