博客后台开发 03：部署与 CI 的完整链路

这条链路上发生什么

前两篇讲的是后台本身。这一篇讲从「在浏览器里点保存」到「GitHub Pages 上的站点更新」之间发生的事。

这条链路不长，但它是整个项目里失败次数最多的部分。不是因为它复杂，而是因为它横跨了三个 Git 仓库、两套身份认证、以及一个我至今没有完全搞懂的 Bash 默认行为。

文章的顺序大致是失败发生的顺序：先讲清楚三个仓库怎么分工，再讲本地的三种发布模式，然后是 CI 上的四个坑，最后讲一个我自己引入又修掉的回归。

三个仓库的分工

先把结构讲清楚，因为后面所有的权限问题都源于这里。

仓库 可见性 内容
Y3148y/my-blog 私密 文章、配置、后台代码、工作流定义
Y3148y/hexo-theme-butterfly 公开 主题定制（CI 从这里拉）
Y3148y/Y3148y.github.io 公开 只有产物：index.html、css/、js/

工作流为什么必须在有源码的仓库

一个常见的误解是「Pages 仓库才是站点的工作目录，工作流当然放那里」。但那个仓库里没有源码——它的顶层条目全是构建产物，连 package.json 都没有。

拿产物构建产物是不可能的。 所以工作流只能待在有源码的地方：私密的 my-blog 仓库。它在 push 到 main 时触发，构建完再把产物推到 github.io。

这个设计有一个实际好处：源码仓库是私密的，所以不用公开也能自动部署。如果你把源码和产物放同一个公开仓库，等于把文章源文件和后台代码都暴露了。

主题定制为什么必须 Fork

站点的油画画廊、音乐播放器、访客欢迎卡、L2D 挂钟，全在 themes/butterfly 里。而这个目录在我的主仓库里是被 .gitignore 忽略的——因为它是独立 clone 下来的主题仓库，不应该被主仓库追踪。

后果是：定制只存在于我的本机。Actions 跑在 GitHub 的云端机器上，看不见我的硬盘。

三种发布模式

后台提供三种发布模式，覆盖不同场景：

模式 执行内容 适用
构建并部署 hexo clean → generate → deploy 日常，本机一步到位
仅本地构建 hexo clean → generate 只看效果，不上线
提交给 Actions git commit + git push 云端构建，换电脑也能发

第三种是「提交给 Actions」：后台只做提交和推送，构建交给云端。它的实际价值有两个——一是换电脑也能发（只要有仓库权限），二是构建过程不占用本机。

注意这里的关键信息是身份被正确解析成了 Y3148y——说明令牌有效、认证通过，问题在授权范围。

怎么区分经典 PAT 和 Fine-grained？看响应头：

经典 PAT 的 X-OAuth-Scopes 一定有值。空值 + 出现 expiration 头，说明这是 Fine-grained PAT。

而 Fine-grained PAT 的权限模型完全不同：它没有「repo 作用域」这回事，取而代之的是：

  • Repository access —— 必须显式勾选每一个要访问的仓库
  • Permissions —— 每个仓库单独勾，Contents 可以是 Read 或 Read and write

我最初的配置里只授权了内容仓库，Pages 仓库没勾上。所以克隆主题正常，推送产物 403。

所以必须把 Y3148y.github.io 也加进授权列表，Contents 权限设为 Read and write。

顺带一个更要紧的提醒：排查过程中我把一个完整的 PAT 明文贴进了对话里，这属于明文密钥泄露，标准处置是立刻吊销重建。更安全的做法是让 CI 自己打印脱敏结果——上面那个诊断步骤就是这么设计的，它输出的是身份、权限位、HTTP 状态码，一个字符的令牌都不会打印。排查令牌问题时不要把令牌拿到本地 curl。

怎么在本地验证工作流

坑三那个 bug 之所以要推四次才修好，根本原因是：工作流脚本我一次都没在本地执行过就推上去了。

补上本地验证之后，很多问题一次就确认了。三个例子：

验证诊断脚本。 用桩 curl 在 bash -e 下实跑三种令牌场景（Fine-grained、经典 PAT、无权访问），校验退出码：

验证 --force 的必要性。 不要靠「看起来会失败」，而是构造一个非空的本地远端复现 non-fast-forward，再验证 --force 能修复它。

验证降级重试。 在沙箱仓库里把本地 http.proxy 指向死端口 127.0.0.1:1，使直连必然失败，然后验证带 -c 覆盖参数的代理重试能成功。

最后一条是重点：用构造出来的必然失败代替碰运气。 网络抖动的失败率没法控制，测十次可能只碰到两次；而「把代理指向死端口」让失败率变成 100%，测一次就是确定的结果。

同样的思路也可以用来验证 bash 片段的错误处理——不要写「期望它失败」，要写「构造一个让它必然失败的输入，然后断言错误信息里出现了什么」。

小结

  1. 产物仓库不能构建产物，工作流必须待在有源码的地方。这也顺带让私有源码仓库能自动部署。
  2. 主题定制用 Fork 而不是 patch，因为只有 Fork 保留了和上游同步的能力。
  3. 手写 git push 让令牌不进仓库历史，hexo deploy 做不到这一点。
  4. 预检把慢失败变快，但要区分认证类和网络类错误，前者阻断、后者警告。
  5. 只有网络类错误才值得重试，认证类换代理也是 401。
  6. ${{ secrets.* }} 不会自动变成 shell 变量，每个用到的步骤都要写 env: 映射。
  7. git init 后推送 Pages 必须 --force，因为那是覆盖语义。
  8. bash -e 会让诊断脚本自杀，匹配不到内容的 grep + pipefail 就是死亡组合，用 set +e 兜住。
  9. Fine-grained PAT 要逐仓库授权，它没有「repo 作用域」这回事。
  10. --force 不能滥用，只有「全量覆盖产物」才需要，源码仓库必须快进推送。
  11. 工作流脚本必须先在本地跑通再推，用构造出来的必然失败代替碰运气。

到这，「博客后台开发」这个系列就写完了。三篇分别是整体架构、frontmatter 序列化、部署与 CI。后续如果有新的踩坑，我会继续补在对应的篇目里。
