RabbitMQ 面试系列 02：可靠性、消费与消息治理

发表于2026-10-01|更新于2026-10-01|技术学习
|浏览量:

本文是 RabbitMQ 面试系列的第二篇，聚焦「消息到底会不会丢」这条主线：生产端可靠性、消费端 ACK 与幂等、QoS 流控、延迟消息、死信与重试体系。

一、可靠性模型：消息到底会不会丢

这是面试和实战中最重要的一章。几乎所有「MQ 丢消息」的线上事故，都能追溯到本章的某一个环节被漏配。

1.2 生产端可靠性三件套

1.2.1 持久化：声明持久 + 消息持久

注意「持久化」是两件事，很多人只做了一件。

为什么只有 Quorum Queue 才真正「持久」？

deliveryMode=2 的语义是「消息应该写到磁盘」。但：

  • Classic Queue：消息进入内存，触发刷盘（vm_memory_high_watermark 或每 5 秒）时才落盘。节点宕机 → 内存里的消息全丢。
  • Quorum Queue：消息在 Leader 上就通过 Raft 复制到多数派并写入磁盘，确认时才返回 ack。节点宕机 → 已确认的消息仍在其它副本上。

一句话：持久化交换机/队列 + 持久化消息 + Quorum Queue，三者缺一不可。只做前两件，在节点宕机时依然会丢。

1.2.2 Publisher Confirms：唯一可靠的生产确认

默认情况下，channel.basicPublish() 是一个「即发即忘」（fire-and-forget）的调用——它只是把数据写进本地 socket 缓冲区就返回。你无法知道 Broker 是否收到了。

Publisher Confirms 是 Broker 对生产者的逐条/批量确认机制：

Confirm 的粒度与语义：

特性 说明
确认粒度 每个 Channel 独立，不是每个连接
delivery tag Channel 内单调递增的消息序号
multiple=true 表示该序号及之前所有消息都已确认
确认时机 Classic：写入队列后；Quorum：多数派副本落盘后
未确认的消息 Channel 关闭时，Broker 会对所有未确认消息发 nack

面试陷阱：「basicPublish 没抛异常 = 消息发送成功吗？」
答：不是。 basicPublish 抛异常只说明「参数非法 / Channel 已关闭 / 连接断了」。消息是否被 Broker 接收，只有 confirm 说了算。

1.2.3 mandatory + Return：捕获「路由不到」的消息

这是两个完全独立的机制，但必须配套使用。

机制 触发条件 作用
Publisher Confirm 消息被 Broker 接收（哪怕没路由到任何队列） 防止「消息根本没到 Broker」
mandatory + Return 消息被 Broker 接收了，但路由不到任何队列 防止「消息到了 Broker 但被丢弃」

关键理解：当消息无法路由时，Broker 仍会确认（ack）它。因为从 Broker 的角度看，它确实收到了这条消息。所以光有 confirm 是发现不了「路由失败」的。

配合 alternate-exchange 使用，就能做到「路由失败 → 消息进入兜底队列 → 告警」。

1.2.5 AMQP 事务：为什么不推荐

AMQP 事务存在，但 RabbitMQ 官方明确不推荐，原因是性能损耗极大。

官方原文大意：使用事务会使吞吐下降约 250 倍。因为事务需要给 Channel 加全局锁，且事务内缓冲消息有数量上限（4.3 新增 channel_tx_message_max，默认 10000，超出直接抛 precondition_failed）。

替代方案：

需求 推荐方案
确认消息被接收 Publisher Confirm（异步，高性能）
消息本地事务一致性 Outbox 模式（系列第 04 篇详述）
端到端事务 不可能，别追求；用幂等 + 状态机

面试高分回答：「AMQP 的 tx.select/commit 是同步阻塞的全局事务，会给 Channel 加锁，吞吐下降一个数量级以上。生产环境应该用 Publisher Confirm 做异步确认，本地事务与消息发送的一致性用 Outbox + 定时补偿来解决，而不是用分布式事务。」

1.2.6 生产端可靠性检查清单

  • 交换机 durable=true
  • 队列 durable=true + x-queue-type=quorum
  • 消息 deliveryMode=2
  • 开启 confirmSelect() 并注册 ConfirmListener
  • basicPublish(..., mandatory=true) 并注册 ReturnListener
  • 交换机配置 alternate-exchange
  • 消息带 messageId（用于消费端幂等）
  • 消息带 correlationId / header 里的 traceId（用于全链路排查）
  • ConnectionFactory 配置 automaticRecovery=true + networkRecoveryInterval
  • requestedHeartbeat（默认 60s）
  • Channel 用完归还（channelFor() 或 ChannelPool）

1.3 消费端可靠性

1.3.1 手动 ACK：把控制权交到自己手里

参数二 multiple 的含义：

  • multiple=false（几乎总是用这个）：只确认/否掉这一条。
  • multiple=true：确认/否掉该 deliveryTag 及之前所有未确认的消息。

⚠️ multiple=true 是经典 bug 源：如果你用 nack(deliveryTag, true, requeue=false)，会把这一批所有未确认消息全部打进去。除非你明确在批量处理，否则永远用 false。

1.3.2 ⭐ ACK 的正确位置（最高频面试题）

问题：basicAck 应该在业务处理前还是处理后？

但「ACK 在业务处理之后」也有一个问题：如果业务处理是「写数据库 + 调 HTTP」，在「写完数据库、还没 ACK」时崩溃 → 消息重投 → 数据库被写两次。

终极解法：ACK 与本地事务绑定。

面试标准答案：
「ACK 必须在业务处理成功之后。但仅仅这样还不够——如果业务处理成功、ACK 之前进程崩溃，消息会重投导致重复消费。根本解法是消费端幂等：用业务唯一键（orderId）做去重表或唯一索引，重复执行时识别为已处理并直接 ACK。同时可以用 Spring 的事务感知 ACK，把 ACK 时机绑定到本地事务提交之后。」

1.3.3 幂等：at-least-once 的唯一解药

RabbitMQ 保证 at-least-once（至少一次）投递。这意味着重复消费是必然事件，而不是异常。

常见的「重复消费」触发场景：

场景 说明
消费者处理成功但 ACK 前崩溃 重投
连接不稳定导致 basic.recover 重投
消费者超时（4.3 quorum consumer timeout） 退回并重投
手动 basicNack(requeue=true) 重投
应用重启 未 ACK 的消息重新投递
Khepri/Quorum 的 Leader 切换 未 ACK 的消息重新投递

三种幂等实现方案：

方案 A：唯一索引（最可靠，推荐）

方案 B：Redis 幂等表（性能高，有风险）

⚠️ 风险：Redis 幂等表的「设置标记」和「执行业务」不是原子的。若设置标记后、业务执行前崩溃 → 消息被标记为已处理，但业务没执行 → 永久丢失。

正确姿势：先执行完业务，最后再写幂等标记（这样重复执行会重复跑业务，但因为业务本身幂等，也不怕）。或者干脆用数据库唯一索引。

方案 C：状态机（最贴合业务）

这是最好的幂等：把幂等逻辑内建在业务状态转移里，天然正确。

1.4 三大语义：at-most-once / at-least-once / exactly-once

语义 配置 保证 风险
at-most-once（至多一次） autoAck=true 或 basicNack(requeue=false) 消息最多处理一次 丢消息
at-least-once（至少一次） autoAck=false + basicAck 消息至少处理一次 重复处理
exactly-once（恰好一次） ❌ MQ 层面不存在 — —

为什么 exactly-once 做不到？

「恰好一次」要求「消息被处理且仅被处理一次，且处理结果持久化」。问题在于：处理逻辑通常涉及外部系统（数据库、HTTP 接口），MQ 无法参与这个事务。

  • MQ 内部事务（txSelect）只能保证「消息的批量收发原子性」，不能覆盖业务逻辑。
  • 两阶段提交（XA）：AMQP 1.0 有 transactional-state，但需要所有参与方都支持 XA，Java 客户端生态支持度极低，JMS 有 XA 但 RabbitMQ 的 JMS 客户端支持不完整。
  • RocketMQ 的「事务消息」是另一条路：它用「半消息 + 状态回查」实现「本地事务与消息发送的原子性」，但它保证的不是「业务执行恰好一次」，而是「业务与发消息的原子性」，业务侧仍需幂等。

面试标准答案：
「exactly-once 在分布式场景下无法真正实现。行业共识是 at-least-once + 幂等 = 业务上的 exactly-once。这是 Google SRE 和所有主流 MQ 厂商的官方立场。实现幂等的最佳方式是数据库唯一索引或状态机，而不是分布式事务——因为分布式事务的性能损耗和运维复杂度通常远高于幂等方案。」

二、消费语义与流量控制

2.1 Competing Consumers：轮询分发

当多个消费者监听同一个队列时，RabbitMQ 会**轮询（round-robin）**分发消息：

这是水平扩容的基础：部署 10 个消费者，同一个队列，消息被均匀分摊。

⚠️ 重要前提：这是「轮询分发」，不是「广播」。如果你想让每个消费者都收到全量消息，需要每个消费者一个队列，然后用 fanout 交换机绑定。

2.2 预取（Prefetch / QoS）

2.2.1 为什么需要 QoS

basic.qos 控制「最多允许多少条未确认消息」。

如果不设置：RabbitMQ 会尽可能多地推送消息给消费者（尽可能填满 TCP 窗口）。

设置 QoS=10：

2.2.2 参数详解

global 参数（4.x 起 global_qos 已移除；Quorum Queue 完全不支持 global QoS）：

global 含义
false（推荐） per-consumer QoS：每个消费者各自计算
true per-channel QoS：整个 Channel 所有消费者共享这个配额

⚠️ 常见错误：basicQos(100, true) + 一个 channel 上开 10 个消费者 → 这 10 个消费者共享 100 条，每个只有 10 条。

⚠️ Quorum Queue 上 global=true 会直接导致 Channel Error：官方明确写了「Quorum queues do not support global QoS. If an attempt is made to consume from a quorum queue from a channel with global QoS activated, a channel error will be returned.」
所以从 Quorum 队列消费时必须用 per-consumer QoS（RabbitMQ 官方推荐的 global=false 语义）。

永远用 global=false。

2.2.3 怎么设这个值？

场景 建议 prefetch
单条处理耗时 < 50ms（轻量） 较大（100 ~ 1000），减少网络往返
单条处理耗时 50ms ~ 1s（常见业务） 10 ~ 50
单条处理耗时 > 1s（重任务） 1 ~ 5
需要严格顺序 1（配合单活跃消费者）
内存敏感 / 消息体大 1 ~ 10

核心原则：prefetch × 消息体大小 × 消费者数 应该远小于可用内存。

例：消息 100KB，prefetch 100，10 个消费者 → 100MB 常驻内存。看起来不多，但如果同时有 10 个这样的队列，就是 1GB。

2.2.4 QoS 与吞吐/延迟的权衡

  • prefetch 太小（如 1）：每次处理完要等 Broker 推送下一条，网络往返成为瓶颈，吞吐下降。
  • prefetch 太大（如 10000）：内存压力大；一旦某个消费者卡住，它手里攥着 10000 条消息，其他消费者已经处理完了 → 负载严重不均衡。
  • 经验公式：prefetch ≈ 单条处理耗时(ms) × 目标 TPS ÷ 1000。例如单条 100ms、目标 1000 TPS → prefetch ≈ 100。

2.3 Push vs Pull

RabbitMQ 只有一种「推送」模式——basic.consume，但它本质上仍是拉取：

常见误解：「basic.consume 是 Broker 主动 push 给消费者」。更准确的说法是：Broker 在消费者 socket 可读时尽快写入，而 TCP 流控（发送窗口）限制了突发量。prefetch 则是在应用层限制了「未确认消息数」，从而间接限制了 TCP 窗口内可容纳的消息数。

2.3.1 basic.get：真正的拉取

basic.get 的致命缺点：

  1. 没有 QoS 机制，一次只能拿一条。
  2. 没有「等待」机制——队列空时立即返回 null，必须自己 sleep 重试（轮询浪费资源）。
  3. 每次调用有 RTT 开销，高吞吐下性能远不如 basic.consume。

结论：除「管理工具临时取一条看看」这类场景，业务代码一律用 basic.consume。

2.4 autoAck 的坑

autoAck=true 时，Broker 在投递成功的瞬间就把消息标记为已确认并从队列删除。如果消费者随后处理失败（甚至根本没开始处理就崩溃了），消息永久丢失。

唯一可以接受 autoAck=true 的场景：消费者只是「读了就扔」（如日志采集转发到 Kafka、监控打点）。这种场景下丢消息是可接受的。

2.5 毒消息与「NACK requeue 死循环」

这是生产环境最经典的 RabbitMQ 故障。

2.5.1 问题现象

如果某条消息永远处理不了（比如 JSON 格式损坏、字段缺失导致 NPE、调用第三方接口返回非法数据），那么：

  1. NACK requeue → 消息回到队头
  2. Broker 立刻把它再推给某个消费者
  3. 消费者再失败，再 NACK，再推回
  4. 无限死循环

后果：

  • 该消费者 CPU 100% 打满
  • 其他正常消息被这个死循环挤占（队头阻塞）
  • 消息 redelivered 计数疯涨，日志被刷爆
  • 如果有监控，可能会误判为「流量激增」

2.5.2 五种解法（从优到劣）

    flowchart TD
    START[消费失败] --> Q{失败原因可分类?}

    Q -->|可重试的瞬时故障| R1[方案1 有限次重试<br/>内存计数 或 retry 队列]
    R1 --> R1D{超过最大重试次数?}
    R1D -- 否 --> RECOVER[投递到 retry 队列<br/>带 TTL 延迟后回主队列]

方案 2：Quorum Queue 的 delivery-limit（最优雅）

Broker 侧兜底，不依赖应用代码正确性：

消息被判定「投递失败」5 次后自动进 DLX。即使你的代码写的全是 basicNack(requeue=true)，也不会死循环。

⚠️ 4.3 的行为变了，很多人踩坑：
delivery-limit 现在基于 delivery-count（只统计真正的投递失败），而 0-9-1 的 basic.nack(requeue=true) 不会递增 delivery-count。
所以「全是 nack 的代码」在 4.3 上不受 delivery-limit 保护，这反而让 basicNack(requeue=true) 可以放心用于「临时失败重试」。

反过来，basic.reject(requeue=true) 仍然会计数，5 次后照样进 DLX。

也就是说：4.3 上防毒消息要盯的是「reject 次数」和「消费者超时/崩溃重投」，不是「nack 次数」。 详见 5.2.5。

想要和内容无关的绝对兜底，还是要显式配 delivery-limit（默认 20）。

方案 3：跳过 + 落库（适合脏数据）

方案 4：直接进死信（requeue=false）

方案 5：requeue=true（只在有防护时使用）

只有在配合方案 1 或 2 的前提下才能用。裸用必炸。

2.5.3 consumer_timeout：消费者「假死」的自保

语义：消费者持有 unacked 消息超过这个时间，RabbitMQ 会关闭该 Channel 并把消息退回队列。

它能救的场景：消费者进程还活着、线程还在，但业务逻辑卡死（比如等待一个永不返回的 HTTP 调用）。否则这条消息会永远占着不释放。

它救不了的场景：消费者进程崩溃（此时连接断开，消息立即退回）。

注意：Classic Queue 和 Stream 不评估 consumer timeout（4.3 变更）。需要这个能力请用 Quorum Queue。

2.6 消费者取消（Cancel）与连接恢复

消费者被取消的常见原因：

原因 说明
basic.cancel Broker 主动取消（如队列被删除）
Channel 关闭 连接断开、协议错误、precondition-failed
队列被删除 队列删了，消费者自动被取消
队列不匹配 队列类型、参数不一致导致 406

automaticRecovery 能恢复什么、不能恢复什么（Java 客户端）：

✅ 能恢复：连接中断后自动重连、恢复消费者和发布者、恢复拓扑声明（重新 declare）。
❌ 不能恢复：AMQP 事务状态、channel.txSelect 状态、正在执行但未确认的确认监听器状态、以及原本应该在连接上的东西被清理掉的情况。
❌ 不会恢复：channel.basicNack 之后的消息状态。

关键点：自动恢复会重新投递未确认的消息。所以业务幂等不是可选项。

⚠️ automaticRecovery 不是万能的。生产环境更推荐用多节点 + 多实例 + 主动重连封装，或者依赖 Kubernetes 的健康检查自动重启 Pod。

本章小结

  • 丢消息的根因永远是「少配了一个确认」：生产端少 confirm / 少 mandatory，消费端少 ACK / 少幂等。
  • Publisher Confirm（消息到没到 Broker） 和 mandatory+Return（到没到队列） 是两个独立机制，必须配套。
  • exactly-once 不存在，正确姿势是 at-least-once + 幂等。
  • prefetch 永远用 global=false；数值按处理耗时估算，不要拍脑袋。
  • 毒消息防护优先用 Quorum Queue 的 delivery-limit（Broker 侧兜底，不依赖应用代码正确性）。

三、延迟消息：TTL、死信与延迟重试

延迟消息是订单场景的刚需：15 分钟未支付自动关单、7 天未发货自动退款、优惠券到期提醒。面试官几乎必问。

先破除一个常见误解：很多资料会说「RabbitMQ 4.3 给 Quorum Queue 加了 scheduled delivery，所以能原生做延迟消息」。
这是不对的。 4.3 的新特性叫 Delayed Retry（延迟重试），它的作用域只有「被消费者退回的消息」，
不能用来实现「15 分钟后发一条关单消息」。

本章只讲两件事：

  1. 真正的延迟投递怎么做 → TTL + DLX（方案一）
  2. 消费失败后的重试退避怎么做 → Quorum Delayed Retry（方案三）

3.2.2 ⚠️ 头部阻塞（Per-Queue TTL 的致命缺陷）

这是 TTL + DLX 方案最大的坑，也是面试高频陷阱。

规则：RabbitMQ 只在消息到达队列头部时检查它是否过期。如果一条消息过期了，但它前面有未过期的消息，它不会被移除。

看起来没问题？因为队列级 TTL 是统一的。

真正的坑：队列级 TTL 与消息级 TTL 混用时

结果：

  • 先放入 1 小时的消息 M1
  • 再放入 10 分钟的消息 M2
  • 10 分钟后 M2 已到期，但它前面是 M1，所以 M2 卡在队列里！
  • M2 本该 10 分钟执行，实际要等 60 分钟后 M1 过期才轮到它

这就是「头部阻塞」：短延迟消息被长延迟消息堵住，延迟时间完全失真。

3.2.3 头部阻塞的解法

解法一：按延迟时长分队列（推荐，最简单可靠）

同一队列内所有消息 TTL 相同 → 就不存在头部阻塞。

代价：需要预估延迟档位。但业务上的延迟需求本来就是分档的（5 分钟 / 30 分钟 / 24 小时），所以这个代价完全可以接受。这是绝大多数生产系统的做法。

解法二：Spring 的 x-delayed-message 声明（需插件）

见 3.3 节。

解法三（仅适用于「消费失败后的重试」）：Quorum Queue Delayed Retry（4.3+）

见 3.4 节。

⚠️ 注意：它不能解决头部阻塞，因为它只处理「被退回的消息的重试退避」，不是通用延迟投递机制。
如果你要做「15 分钟后发关单消息」，只能用上面的解法一（TTL + DLX 分档队列）。

3.3 方案二：x-delayed-message 插件

3.3.1 状态：已归档，不要在新项目使用

重要：RabbitMQ 官方已将 rabbitmq_delayed_message 插件归档（archived），不再维护。
官方明确说明：不会为 4.0+ 的新特性做适配，也不接受新的功能请求。

所以：生产环境请优先用 TTL+DLX；只有存量系统或明确需要时再用插件。

问题 说明
内存表，非持久 延迟消息存在 Mnesia 内存表中，Broker 重启 / 节点故障 → 延迟消息全部丢失

3.4 方案三：Quorum Queue Delayed Retry（4.3 新特性）⭐

⚠️ 先纠正一个常见的误解：Quorum Queue 在 4.3 并没有「通用延迟消息 / scheduled delivery」功能。
4.3 真正新增的是 Delayed Retry（延迟重试），它的作用范围只有「被消费者退回的消息」，
不能用来实现「15 分钟后发一条关单消息」这类业务定时任务。

换句话说：

需求 该用什么
「消息被消费失败了，等 10 秒再重试」 ✅ Quorum Delayed Retry（4.3）
「15 分钟后主动发一条关单消息」 ❌ 只能用 TTL + DLX（本章 8.2）

工作原理：当消息被退回（reject / nack / modify）且开启了 delayed retry 时，Broker 会把它在内部按「ready-at 时间戳」暂存到一个延迟结构里，延迟期满后才重新变为可投递状态。

3.4.1 配置

⚠️ --apply-to 必须写 quorum_queues，写 queues 不生效。

3.4.2 四种 retry type（关键，选错就不生效）

type 含义 覆盖场景
disabled 不延迟（默认值） —
all 所有被退回的消息都延迟，不论 delivery-count 是否递增 覆盖最广，不确定行为时选它
failed 只延迟 delivery-count 递增的消息（reject、AMQP 1.0 modified(delivery_failed=true)、带 pending 消息的 channel 终止） 只针对「真失败」退避
returned 只延迟 delivery-count 不递增的消息（nack、AMQP 1.0 modified(delivery_failed=false)） 只针对「主动退回」退避

3.4.3 退避公式（线性，不是指数）

以 min=1000ms、max=30000ms 为例：

退回次数 计算 实际延迟
第 1 次 1000 × 1 1000ms
第 2 次 1000 × 2 2000ms
第 3 次 1000 × 3 3000ms
第 4 次 1000 × 4 4000 → 被 max 截断为 30000ms
第 5 次及以后 继续增长 30000ms

注意是「线性」不是「指数」。很多资料写成 2^n，那是错的。

还有一个官方特意强调的点：「a message’s delivery-count is only incremented for failures. This means not all return types will cause the message to be delayed longer than the minimum.」

也就是说，如果你用 basic.nack(requeue=true)，而 type 配的是 failed，那么 delivery-count 不递增，退避永远停在 min，等于没有退避效果。这就是为什么 type 选错会很隐蔽。

3.4.4 优势与代价

优势：

  • Broker 侧实现，应用代码零改动，也就不存在「应用重启丢重试状态」的问题。
  • 持久化 —— 在 Raft 磁盘日志里，Broker 重启不丢。
  • 消费线程不阻塞 —— 退避期间消息不在队列里，不占 prefetch 配额。
  • 管理界面可见 —— delayed retry 配置、延迟消息数量、重试状态都能看。

代价与限制：

  • 只能用于「重试」，不能用于「定时投递」 —— 这是最容易搞错的地方。
  • 仅支持 Quorum Queue（Classic 和 Stream 不支持）。
  • 延迟中的消息不算 ready，管理界面 Messages Ready 可能显示 0，需要看专门的 delayed 指标。
  • 需要 4.3+ 节点。

四、死信队列与重试体系

4.1 死信（Dead Letter）机制

4.1.1 什么消息会进入死信队列？

四种触发条件：

触发条件 场景
basic.reject(requeue=false) 消费者主动拒绝
basic.nack(requeue=false) 消费者批量否定
消息 TTL 过期 x-message-ttl / expiration
队列达到长度上限 x-max-length / x-max-length-bytes 触发 overflow

附加触发条件（3.12+）：

触发条件 场景
delivery-limit 超限 Quorum Queue 投递次数超限（默认 20）
队列 leader 不可用 maxlen 策略下返回 REJECTED
目标队列不可达 开了 at-least-once DLX 时，内部消费者会持续重试（不是「耗尽」，所以要监控 DLQ 堆积）

官方定义：一条消息如果被拒绝、过期、或因队列长度超限而被丢弃，并且队列配置了 DLX，那么这条消息会被重新发布到 DLX。

4.1.2 DLX 三件套参数

如果没有配置 DLX 会怎样？

  • 消息被 reject(requeue=false) / nack(requeue=false) → 被丢弃（或根据 overflow 策略处理）
  • 消息 TTL 过期 → 被丢弃
  • 队列满触发 drop-head → 被丢弃

反模式：很多项目只声明了 DLX，却把 DLX 指向一个不存在的交换机，或者 DLX 上没有任何队列绑定——结果和没配 DLX 一样，消息照样丢。必须端到端验证。

4.2 x-death 头：死信分析的黄金数据

每条进入死信队列的消息都会带一个 x-death 头，记录它的「死亡档案」：

字段 说明
queue 消息最后所在的队列
reason 死信原因：rejected / expired / maxlen / delivery_limit / maxlen_bytes
count 该消息在这个队列被死信的累计次数
exchange / routing-keys 死信发布时用的交换机与 routing key
time 最近一次死信的时间戳

4.2.1 基于 x-death 的智能重试

注意 x-death 的数组顺序：RabbitMQ 会按「最近一次死信在前」排列，且同一个队列只保留一条记录（count 累加）。但中转队列（delay/retry）的记录会叠加，所以需要主动过滤，只看业务队列的记录。

4.2.2 ⚠️ x-death 的两个坑

坑 1：类型不是 Long，是 Integer 或 Long 混用

count 和 time 在不同版本/路径下可能是 Integer 或 Long。必须用 ((Number) obj).longValue()，不能直接强转 (Long)，否则 ClassCastException。

坑 2：x-death 会在「再次死信」时被合并

一条消息从 order.pay.queue 死信到 retry.queue，又从 retry.queue 死信回 order.pay.queue，x-death 会有两条记录（不同 queue），但 order.pay.queue 那条的 count 会继续累加。所以基于 count 的重试上限判断是可靠的。

4.3 死信循环（Dead Letter Cycling）

如果 DLX 又指回了原队列，就会无限循环。

⚠️ RabbitMQ 没有内置的死信循环检测（这是刻意为之——有些场景确实需要循环，比如「重试 3 次后再回到主队列」这种受控循环）。

防护手段：

  1. 用 x-death 的 count 字段在消费端判断，超过阈值直接进最终 DLQ（这是唯一可靠的方式）。
  2. 保证 DLX 和源队列在不同交换机上。
  3. 监控 DLQ 深度，异常增长立即告警。

4.4 重试架构的三种实现

4.4.1 方案 1：Spring Retry + DLX 重试队列 ⭐ 主流方案

⚠️ 注意 RetryInterceptorBuilder 的几个易错点：

  • stateless() = 无状态重试（立即重试）；stateful() = 有状态（用消息 ID 去重，需要 RetryOperationsInterceptor + 消息 ID 支持，且要求 advised 链在单一消费线程上）。
  • .maxAttempts(3) 是总次数（首次 + 2 次重试），不是「重试 3 次」。
  • stateless 模式下重试是在消费线程里完成的，意味着重试期间这个消费者线程被占住。长延迟重试请用方案 2。

4.4.2 方案 2：retry 队列 + TTL 递增（长延迟重试）⭐⭐ 最推荐

思路：不做内存重试，而是把失败消息投递到一个带 TTL 的 retry 队列，TTL 到期后通过 DLX 回到主队列。消费线程立即释放。

4.4.3 方案 3：Quorum Queue 的内置延迟重试（4.3+）⭐ 最省心

4.3 起，Quorum Queue 内置「延迟重试」，不需要任何应用代码。

退避公式：min(min_delay × delivery_count, max_delay)，线性递增，不是指数。

四个关键细节（细节决定成败）：

  1. --apply-to 必须写 quorum_queues，写 queues 不生效。
  2. delayed-retry-type 选 all 最稳。如果选 failed 或 returned，而你的代码用的是 basic.nack（delivery-count 不递增），退避会永远停在 min，等于白配。
  3. delayed-retry-min 在启用时必填，-max 可选（默认等于 min）。
  4. 它只是退避，不是重试次数上限 —— 真正决定「什么时候放弃」的还是 delivery-limit（默认 20）。两者是独立机制，配合使用。

详见 3.4 节的完整说明（含四种 retry type 的语义差异）。

4.5 Spring Boot 四种 Recoverer 对比

RetryInterceptorBuilder 的 .recoverer() 有四个常用实现：

Recoverer 行为 适用
RejectAndDontRequeueRecoverer basicNack(requeue=false)，消息进队列 DLX 队列配了 DLX
RequeueRecoverer basicNack(requeue=true)，消息回原队列 ⚠️ 会死循环
ImmediateRequeueMessageRecoverer basicNack(requeue=true)，消息头会去掉 x-death（防止死信循环） 简单重试
DeadLetterPublishingRecoverer 重新发布到指定 exchange/routing key ⭐ 最推荐

强烈推荐 DeadLetterPublishingRecoverer，因为：

  1. 可以动态选择 DLQ（按异常类型分流）。
  2. Quorum Queue 可以开启 at-least-once 死信投递，此时这个 recoverer 的投递是可靠的（⚠️ 但默认是 at-most-once，必须按 5.2.3 显式配置）。
  3. 消息带上了 x-exception-message、x-original-exchange 等排查头。

本章小结

  • TTL + DLX 是最通用的延迟方案，但必须按延迟档位分队列，否则头部阻塞会让延迟完全失真。
  • x-delayed-message 插件已归档，内存表不可靠，新项目别用。
  • Quorum Queue 的 delayed retry（4.3+） 最省心的重试方案，但不能用于定时投递。
  • 死信防护三件套：TTL+DLX 延迟队列、x-death 计数、delivery-limit 兜底。
  • 重试要区分瞬时失败和毒消息：前者可重试，后者直接 DLQ + 告警。
  • DLQ 必须有监控告警和人工处理流程，否则等于没配。
