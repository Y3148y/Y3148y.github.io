1.1.1 ⚠️ Channel 不是线程安全的

这是 Java 客户端最高频的踩坑点。

一个 Channel 只能在一个线程内使用。不要在多线程间共享 Channel。

AMQP 协议规定：同一 Channel 上的帧必须按发送顺序排列。多个线程并发使用一个 Channel 会导致帧交错，Broker 会以 PRECONDITION_FAILED - unknown delivery tag 或直接关闭连接的方式报错。

1.1.2 Connection 也不是线程安全的

Connection 的问题不同：它内部有一个「共享的 socket reader 线程」，是线程安全的（多线程 createChannel() 是安全的）。但不要手动关闭它，否则整个应用崩掉。

1.2.1 心跳参数怎么设？

    flowchart LR
    A["consumer_timeout 默认 30min"] --> B["consumer 网络分区<br/>Broker 侧多久发现?"]
    B --> C["心跳超时<br/>= 2 x requestedHeartbeat"]

    style C fill:#e6f0ff,stroke:#36c
    style D fill:#fff0e6,stroke:#e93

问题：「客户端到 Broker 的网络断了（拔网线），客户端多久能发现？」

答案：约 2 × heartbeat。 因为：

  • Broker 侧发心跳 → 客户端收不到（2 个周期无响应）→ 客户端判定 Broker 挂了
  • 客户端发心跳 → Broker 收不到 → Broker 判定客户端挂了
heartbeat 故障发现延迟 评价
0（关闭） 可能永不发现 ❌ 危险
30s（默认） ~60s 合理
10s ~20s 更灵敏，但网络抖动容易误判
60s ~120s 高延迟网络

heartbeat 不能太大：它与「故障切换时间」直接相关。生产环境一般 30s 或 60s。

heartbeat 也不能太小：跨机房网络抖动会导致频繁重连，反而加剧故障。判断标准是「误判成本 vs 发现延迟成本」。

2.3.3 ⚠️ 参数类型必须是 String

ackMode、autoStartup、concurrency、maxConcurrency、prefetch 等属性都是 String 类型，因为它们支持 SpEL 表达式。

2.3.4 并发模型：Simple vs Direct

    sequenceDiagram
    autonumber
    participant B as Broker
    participant CT as Consumer Thread<br/>basicConsume 线程
    participant BT as Business Thread<br/>线程池
    participant U as @RabbitListener 方法

    Note over B,CT: Simple 容器（默认）
    B->>CT: basic.deliver

    BT->>U: 调用监听方法
    U-->>BT: 返回

    Note over B,CT: Direct 容器（低延迟场景）
    B->>CT: basic.deliver
    CT->>U: 消费者线程直接调用
    U-->>CT: ACK
    Note over CT,U: ✅ 无线程切换<br/>延迟更低 但 阻塞会拖慢消费
维度 Simple（默认） Direct

线程切换 有 无
延迟 略高 更低
消费确认线程 与处理线程不同 相同（可安全用 ThreadLocal 存 Channel）

适用 绝大多数场景 低延迟 / IO 多路复用（WebFlux）

2.4 AcknowledgeMode 四种模式

模式 行为 可靠性
NONE 忽略是否成功，Broker 自动确认（相当于 autoAck=true） ❌ 最低
AUTO 容器在 @RabbitListener 方法正常返回时 ACK，抛异常时 NACK(requeue=true) ⭐ 默认，推荐
MANUAL 应用手动调 basicAck/basicNack ⭐ 灵活
MANUAL_IMMEDIATE 同 MANUAL，但 ACK 立即在当前线程发送，不等事务提交 特殊场景

2.4.1 AUTO 模式的陷阱

⚠️ AUTO 模式下抛异常 = 无限 requeue。因为没有重试上限、没有死信策略。

必须配合 .adviceChain() 配置 RetryInterceptorBuilder + DeadLetterPublishingRecoverer，否则任何异常都会导致死循环。

生产建议：

  • JSON 的性能瓶颈通常不在序列化，而在网络和 Broker 磁盘 IO。不要为序列化性能过度优化。
  • 不要用 Fastjson，其历史 CVE 较多，且需要开启 AutoType 有 RCE 风险。

2.6 声明式拓扑

2.6.1 声明式声明

2.6.2 ⚠️ 声明式拓扑的三个坑

坑 1：RabbitAdmin 只在启动时声明一次

RabbitAdmin 在 ContextRefreshedEvent 时自动声明拓扑。之后如果队列被误删，不会自动重建。

setIgnoreDeclarationExceptions(true) 能避免「因为参数不一致导致启动失败」——但这也会掩盖真正的配置错误。生产环境建议配合监控告警。

坑 2：多应用互相覆盖拓扑

如果 3 个服务都声明了 order.pay.queue，但参数不同，会触发 406。

解法：

  • 一个服务负责声明，其他服务只消费（用 autoStartup = false 或不声明）。
  • 或者全部使用 policy 管理治理参数，代码里只声明 durable 和 type。

坑 3：参数类型写成 Long 导致启动就 406

2.7.1 配置项踩坑清单

配置 陷阱
default-requeue-rejected 默认 true，会导致 NACK 后无限重投。必须设 false
publisher-confirm-type 默认 NONE，必须显式设 correlated 或 simple
template.mandatory 默认 false，不开启收不到 Return
listener.simple.concurrency 太小消费不过来，太大 Broker 压力大
listener.simple.prefetch 太小吞吐低，太大内存高
listener.simple.missing-queues-fatal 默认 true，队列不存在会导致启动失败
cache.channel.size 太小会频繁创建 Channel，太大浪费
template.retry 是客户端重试，会阻塞调用线程；请配合服务端重试机制使用

2.8 消费端幂等的三种实现对比

方案 实现 优点 缺点
唯一索引 DB PRIMARY KEY (biz_key)，INSERT IGNORE 绝对可靠，与业务事务原子 需要额外表/字段
Redis SETNX SETNX key 1 EX 3600 性能极高 与业务非原子，有丢消息风险
状态机 UPDATE ... WHERE status = 'PENDING' 最贴合业务，无额外存储 需要设计好状态流转

2.8.1 推荐组合：唯一索引 + 状态机

本章小结

  • Channel 非线程安全，绝不能跨线程共享；高并发用 CachingConnectionFactory(CHANNEL)。
  • Connection 配置重点是 heartbeat 和 automaticRecovery，password 绝不硬编码。
  • Spring 里 ackMode 等参数是 String（支持 SpEL），别写枚举。
  • default-requeue-rejected 默认 true 会导致死循环，务必设 false。
  • publisher-confirm-type 默认 NONE，必须显式开启。
  • JSON 序列化要关 FAIL_ON_UNKNOWN_PROPERTIES，避免字段演进导致消费端崩溃。
  • 幂等优先用状态机 + 唯一索引，Redis SETNX 有丢消息风险。
