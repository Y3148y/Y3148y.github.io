1.6 Outbox 模式：解决「本地事务与消息发送」的一致性

1.6.1 问题本质

    sequenceDiagram
    autonumber
    participant APP as Order Service
    participant DB as Order DB
    participant MQ as RabbitMQ

    Note over APP,DB: 错误做法 两个独立操作
    APP->>DB: 1. UPDATE orders SET status=PENDING
    DB-->>APP: ok
    APP->>MQ: 2. basicPublish order.created
    MQ--xAPP: 连接断了 发送失败
    Note over APP,MQ: 订单创建了 但下游永远收不到通知<br/>数据不一致 且无法自愈

根因：数据库事务和 AMQP 发送是两个独立的资源，无法用同一个事务包裹。

Outbox 方案的思路：把「要发的消息」先写进本地数据库的同一事务里，然后由独立的调度器把消息投出去。

    sequenceDiagram
    autonumber
    participant APP as Order Service
    participant DB as Order DB
    participant SCH as Outbox Scheduler
    participant MQ as RabbitMQ
    participant CON as Consumer

    APP->>DB: ① BEGIN TRANSACTION
    APP->>DB: ② INSERT orders (status=PENDING)
    APP->>DB: ③ INSERT outbox_event (status=NEW)
    APP->>DB: ④ COMMIT 原子生效

    loop 每 1 秒
        SCH->>DB: SELECT * FROM outbox_event<br/>WHERE status=NEW AND next_retry_at <= NOW()<br/>LIMIT 200
        DB-->>SCH: 待发送事件
        SCH->>MQ: ⑤ basicPublish + confirm
        alt 确认成功
            SCH->>DB: ⑥ UPDATE status=SENT
        else 失败
            SCH->>DB: ⑥ UPDATE retry_count+1,<br/>next_retry_at = NOW() + 退避
        end
    end

    MQ->>CON: ⑥ 消费消息
    CON->>CON: 幂等处理

1.6.4 Outbox 的「双写」问题与一致性保证

    flowchart TD
    A[Outbox 记录 status=NEW] --> B{发送结果}

    B -->|成功 confirm ack| C[status=SENT<br/>消息已在 Broker]
    B -->|失败| D[status=NEW<br/>retry_count+1<br/>next_retry_at 退避]
    D -->|无限重试| E{超过告警阈值?}
    E -->|是| F[告警 + 人工介入]
    E -->|否| B

    C --> G{消费者一定收到吗?}
    G --> H[Broker 持久化 + Confirm<br/>保证消息在 Broker]
    H --> I[消费者可能重投<br/>但有幂等保护]

    J[定时对账任务<br/>扫描超时的 PENDING 订单<br/>检查 outbox 是否有未发送] --> K[人工/自动补偿]

    style F fill:#ffe6e6,stroke:#d33
    style I fill:#e6ffe6,stroke:#2a2

Outbox 的残留风险：消息在 Broker 里但消费者因为长时间宕机导致队列堆积 → 消息最终会被消费（只要 Broker 不丢），所以可接受。

唯一的真实风险：Broker 集群整体灾难导致 Quorum 丢失。此时需要定期对账（扫描状态超时的订单，检查业务是否真的没生效），人工补偿。

1.7.2 库存扣减的 SQL（悲观锁 + 状态机）

这个 SQL 同时完成了「检查」和「扣减」，靠 WHERE 里的 total_qty - reserved_qty - sold_qty >= quantity 做乐观校验。

  • 不会出现超卖：条件不满足时 affected rows = 0。
  • 不需要显式加锁：单条 UPDATE 在 InnoDB 行锁保护下原子完成。
  • 比「先 SELECT 再 UPDATE」高效，避免了竞态窗口。

    sequenceDiagram
    autonumber
    participant U as 用户
    participant GW as Gateway
    participant PAY as Payment Service
    participant MQ as RabbitMQ
    participant ST as Stock Service
    participant CP as Coupon Service
    participant NT as Notify Service

    U->>GW: 支付请求
    GW->>PAY: 调用支付网关
    PAY-->>U: 返回支付参数
    U->>PAY: 支付完成 第三方异步回调
    Note over PAY: ⚠️ 必须校验签名 + 金额 + 幂等

    PAY->>PAY: 1 校验签名与金额

    PAY->>PAY: 3 BEGIN TX
    PAY->>PAY: 4 状态机 PENDING to PAID
    PAY->>PAY: 5 插入 payment_log 唯一索引
    PAY->>PAY: 6 写 outbox order.paid
    PAY->>PAY: 7 COMMIT
    PAY-->>PAY: 返回 success 给第三方

    Note over PAY: outbox 调度器 1 秒内发布
    PAY->>MQ: publish order.paid persistent

    par 并行消费
        MQ->>ST: order.stock.queue
        ST->>ST: reserved 转 sold 幂等
        ST-->>MQ: ACK
    and
        MQ->>CP: order.coupon.queue
        CP->>CP: 发放优惠券 幂等
        CP-->>MQ: ACK
    and
        MQ->>NT: order.notify.queue
        NT->>NT: 发送短信/推送
        NT-->>MQ: ACK
    end

    Note over U: 返回成功

1.8 关单服务：延迟消息的完整链路

关单的并发安全：支付回调和关单消息可能同时到达，都试图修改订单状态。

这个 WHERE status IN (...) 就是全链路一致性的关键：

  • 支付回调先执行 → 状态变 PAID → 关单的 affected rows = 0，不释放库存。✅
  • 关单先执行 → 状态变 CLOSED → 支付回调的 affected rows = 0，不发券不扣库存。✅
  • 数据库的行锁 + WHERE 条件保证只有一个能成功。✅

1.10 完整时序图：从下单到关单

    sequenceDiagram
    autonumber
    participant U as 用户
    participant O as Order Service
    participant DB as Order DB + Outbox
    participant S as Outbox Scheduler
    participant MQ as RabbitMQ
    participant INV as Inventory Service
    participant P as Payment Service
    participant C as Close Service

    %% ═══ 下单 ═══
    U->>O: POST /api/orders
    O->>DB: BEGIN
    O->>DB: INSERT orders (PENDING, expire_at=+15min)
    O->>DB: INSERT outbox (order.created)
    O->>DB: INSERT outbox (order.close.delay)
    O->>DB: COMMIT
    O-->>U: 201 Created orderNo

    Note over S: 每 1 秒扫描
    S->>DB: SELECT outbox WHERE status=NEW
    S->>MQ: publish order.created 等待 confirm
    MQ-->>S: basic.ack
    S->>DB: UPDATE status=SENT

    S->>MQ: publish 到 order.delay.exchange
    Note over MQ: 进入 order.close.delay.15min.queue<br/>TTL 15 分钟

    %% ═══ 扣库存 ═══
    MQ->>INV: order.stock.queue
    INV->>INV: 幂等检查 通过
    INV->>INV: UPDATE inventory 条件扣减
    alt 库存充足
        INV-->>MQ: ACK
        INV->>O: 订单置 RESERVED
    else 库存不足
        INV-->>MQ: NACK requeue=false
        MQ->>MQ: order.stock.dlq
        Note over INV,MQ: 告警 + 人工处理
    end

    %% ═══ 支付 ═══
    U->>P: 支付
    P->>DB: BEGIN
    P->>DB: 状态机 PENDING to PAID
    P->>DB: INSERT outbox order.paid
    P->>DB: COMMIT
    P->>MQ: publish order.paid
    MQ->>INV: 确认扣减 reserved 转 sold
    MQ->>INV: 发券 / 积分 / 通知

    %% ═══ 超时关单 ═══
    Note over MQ: 15 分钟到<br/>延迟队列消息过期
    MQ->>MQ: DLX 回到 order.exchange
    MQ->>C: order.close.queue
    C->>C: 幂等检查 通过
    C->>DB: UPDATE orders SET CLOSED<br/>WHERE status IN PENDING RESERVED
    alt affected=0 已支付
        C-->>MQ: ACK 忽略
    else affected=1 未支付
        C->>INV: 释放库存
        C-->>MQ: ACK
    end

1.11 故障场景演练

# 故障场景 注入方式 系统表现 恢复方式 是否有资损
1 发布时进程崩溃 kill -9 订单服务 Outbox 记录为 NEW，消息未发 调度器 1s 后自动发送 ❌ 无
2 Broker 集群宕机 停止全部 RabbitMQ Outbox 持续重试，堆积 Broker 恢复后自动发送 ❌ 无
3 消费时进程崩溃 kill -9 库存服务 未 ACK 消息退回队列 重连后重投，幂等保证只处理一次 ❌ 无
4 消费端重复投递 手动重发同一消息 幂等表拦截 直接 ACK ❌ 无
5 毒消息 发一条非法 JSON NACK → DLQ 告警 + 人工处理 ❌ 无
6 超时关单与支付竞态 并发压测 10w 次 WHERE status IN 保证只有一个成功 — ❌ 无
7 重复支付回调 重复调用回调接口 transactionId 幂等 + 唯一索引 直接返回成功 ❌ 无
8 库存超卖 并发下单同一 SKU WHERE 条件保证不超卖 — ❌ 无
9 DLX 不可达 删除 DLX 队列 Quorum at-least-once DLX（需显式开启） DLX 恢复后自动投递；恢复前源队列会持续保留死信消息 ❌ 无
10 延迟消息丢失 重启 Broker TTL+DLX 依赖的延迟队列本身是 quorum 持久化，不丢 — ❌ 无
11 队列堆积 消费者下线 1 小时 Outbox 积压，队列 Ready 涨 消费者恢复后自动消化 ❌ 无
12 Outbox 表膨胀 Broker 长时间不可用 定时归档 + 告警 Broker 恢复后消化 ⚠️ 需关注

这个 MVP 的设计目标：在任何单点故障下，都不产生资损（不超卖、不重复扣款、不丢订单）。

核心手段只有三个：Outbox（不丢消息）、状态机 + 唯一索引（幂等）、Quorum Queue + DLX（不丢不重不排队）。

1.12 MVP 能力清单

能力 实现手段
不丢消息 Outbox 模式 + Publisher Confirm + Quorum Queue
不重复处理 幂等表唯一索引 + 状态机
不超卖 UPDATE ... WHERE total - reserved - sold >= qty
不丢延迟消息 Quorum Queue 持久化 + TTL+DLX（不依赖内存插件）
不死循环 retry 队列 TTL 递增 + MAX_RETRY + DLX
不堆死信 DLQ 监控告警 + 人工处理流程
路由失败可发现 alternate-exchange + mandatory + ReturnCallback
顺序敏感 需要时用 x-single-active-consumer 或多分片队列
全链路追踪 messageId + correlationId + traceId header
指标可观测 rabbitmq_prometheus + Micrometer + Grafana

本章小结

  • Outbox 模式是「本地事务 + 消息发送」一致性的标准解法，代价是多一张表和一个调度器。
  • 状态机 + 唯一索引是幂等的终极形态，能同时解决重复消费、超卖、支付/关单竞态。
  • Quorum Queue 可以开启 at-least-once DLX（⚠️ 默认 at-most-once，必须配 dead-letter-strategy + overflow: reject-publish），开启后死信机制才真正可靠。
  • 延迟消息用 TTL + DLX 分档队列，避免头部阻塞；Quorum 的 delayed retry 只管重试退避，不做定时投递。
  • 整个 MVP 的设计哲学：接受「至少一次」，用幂等把它变成「恰好一次的业务效果」。
